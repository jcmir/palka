# Контракт персистентности (Persistence Contract)

Документ определяет нормативные требования к долговременному сохранению состояния, конфигурации, таймеров и сообщений системы.

## 1. Персистентные сущности

Служба `service` обеспечивает надежное долговременное сохранение следующих структур данных:

1. **Активные запланированные действия (`ScheduledAction`)**:
   * Для каждого таймера сохраняются: `TimerId`, `ActionKind`, `Deadline` (UTC), `created_at`, `created_by`, `emitted_thresholds` и текущий статус исполнения.
   * **Инвариант фиксации**: Команда установки или отмены таймера подтверждается только после успешной синхронизации записи на энергонезависимый накопитель (`flush`).
2. **Желаемое состояние интернет-шлюза (`desired_state: InternetState`)**:
   * Фиксируется целевое авторитарное состояние доступа в сеть (`Unrestricted` или `Blocked`).
   * Волатильное состояние питания `ShutdownState::InProgress` **НЕ СОХРАНЯЕТСЯ** на диск как постоянное состояние загрузки во избежание ложных срабатываний после включения компьютера.
3. **Состояние ожидающих повтора операций (Pending/Retryable State)**:
   * Если применение правила в `InternetGate` завершилось сбоем, состояние ожидания повтора фиксируется на диск, чтобы повторные попытки продолжились после перезапуска службы.
4. **Очередь сообщений Telegram (`ChatMessageQueue`)**:
   * Буфер неотправленных исходящих сообщений сохраняется до получения явного подтверждения доставки от API.
5. **Конфигурация и защищенные учетные данные**:
   * Сконфигурированный `Child SID`.
   * Белый список Telegram `UserId` и `ChatId`.
   * Хэш PIN-кода (Argon2id).
   * Защищенные учетные данные Telegram Bot API.

## 2. Размещение файлов и защита доступа (Storage Location & ACL)

1. **Каталог размещения**:
   * Данные размещаются в системном каталоге `%ProgramData%\Palka`.
2. **Списки контроля доступа (Filesystem ACLs)**:
   * Каталог и файлы данных ДОЛЖНЫ (SHALL) защищаться системным ACL:
     * `NT AUTHORITY\SYSTEM`: Полный доступ (Full Control);
     * `BUILTIN\Administrators`: Полный доступ (Full Control);
     * `BUILTIN\Users` / Standard Users: **Полный запрет любого доступа (No Access / Deny)**.

## 3. Атомарность записи и обработка сбоев хранилища

1. **Атомарная запись**:
   * Все обновления файлов состояния выполняются по схеме атомарного замещения (запись во временный файл -> сброс дисковых буферов -> атомарное переименование / `ReplaceFile` API) либо через транзакционный журнал.
2. **Обработка невосстановимого повреждения данных**:
   * При обнаружении повреждения файлов состояния (сбой контрольной суммы, синтаксическая ошибка) служба **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНА** делать ложные предположения об успешном применении правил.
   * Статус службы немедленно переводится в `ServiceHealth::Critical`.
   * Факт сбоя регистрируется в системном журнале событий Windows (Event Log).
   * Служба предпринимает попытку отправить экстренное оповещение в Telegram родителям.
3. **Процедура восстановления при старте**:
   1. Считывается конфигурация и `desired_state` сети. Если зафиксировано `Blocked`, шлюз `InternetGate` восстанавливает блокировку до перехода в `ServiceReady`.
   2. Считываются активные `ScheduledAction`.
   3. Вычисляется остаток времени `remaining = Deadline - CurrentUtcTime`:
      * Для `BlockInternet` при `remaining <= 0` — блокировка применяется немедленно.
      * Для `ShutdownComputer` при `remaining <= 0` — действие помечается как `MissedDeadline`, таймер аннулируется, родителю отправляется уведомление в Telegram.
      * При `remaining > 0` — таймер регистрируется в `core` с актуализацией пройденных порогов в `emitted_thresholds`.
