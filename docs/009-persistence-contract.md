# Контракт персистентности (Persistence Contract)

Документ определяет нормативные требования к долговременному сохранению состояния, конфигурации, таймеров и истории сообщений системы.

## 1. Персистентные сущности и инварианты сохранения

Служба `service` обеспечивает атомарное сохранение следующих структур данных:

1. **Активные запланированные действия (`ScheduledAction`)**:
   * Для каждого активного таймера сохраняются: `TimerId`, `ActionKind`, `Deadline` (UTC timestamp), `created_at`, `Initiator`, а также список уже отправленных порогов `emitted_thresholds`.
   * **Инвариант персистентности таймеров**: Никакая команда установки или отмены таймера не считается выполненной (`acknowledged`), пока соответствующие изменения не зафиксированы на энергонезависимом носителе с гарантией синхронизации (flush / fsync).
2. **Текущие состояния шлюзов (`InternetState`, `ShutdownState`)**:
   * Фиксируется текущий режим фильтрации интернета (`Unrestricted` или `Blocked`).
   * При старте системы состояние считывается до активации пользовательского окружения.
3. **Очередь сообщений чата и история (`ChatMessageQueue`)**:
   * Неотправленные исходящие сообщения ребенку/родителю сохраняются в персистентную очередь до подтверждения доставки.
4. **Конфигурация и учетные данные**:
   * Белый список Telegram User ID и Chat ID.
   * Хэш родительского PIN-кода.
   * Сконфигурированный SID целевого пользователя Windows (Child SID).

## 2. Размещение файлов и защита доступа (Storage Location & ACL)

1. **Каталог размещения**:
   * Все персистентные данные размещаются в системном каталоге `%ProgramData%\Palka` (или эквивалентном защищенном системном пути).
2. **Списки контроля доступа (Filesystem ACLs)**:
   * Каталог и файлы данных ДОЛЖНЫ (SHALL) иметь строгие права доступа:
     * `NT AUTHORITY\SYSTEM`: Полный доступ (Full Control);
     * `BUILTIN\Administrators`: Полный доступ (Full Control);
     * `BUILTIN\Users` / Standard Users: **Полный запрет любого доступа (No Access)**.

## 3. Атомарность операций и защита от сбоев (Crash Consistency)

1. **Атомарная запись (Atomic Writes)**:
   * Все изменения файлов состояния обязаны производиться по схеме атомарного замещения (запись во временный файл в той же файловой системе -> `flush` буферов -> атомарное переименование / `ReplaceFile` API) либо через транзакционный журнал (WAL).
   * Повреждение файла состояния в результате внезапного отключения питания или сбоя ОС недопустимо.
2. **Процедура восстановления при старте (Startup Recovery Procedure)**:
   * При запуске службы `service`:
     1. Считывается и верифицируется контрольная сумма файлов состояния.
     2. Загружается `InternetState`. Если зафиксировано `Blocked`, шлюз `InternetGate` немедленно блокирует трафик.
     3. Загружаются активные `ScheduledAction`.
     4. Для каждого таймера вычисляется `remaining = Deadline - CurrentUtcTime`:
        * Если `remaining <= 0` (дедлайн наступил во время выключенного состояния) -> действие немедленно исполняется.
        * Если `remaining > 0` -> таймер регистрируется в планировщике `core` с сохраненными `emitted_thresholds`.
