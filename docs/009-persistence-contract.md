# Контракт персистентности (Persistence Contract)

Документ определяет нормативные требования к долговременному сохранению состояния, конфигурации, таймеров и сообщений системы. Все типы соответствуют [Доменному контракту](./002-domain-contract.md), [Контракту таймеров](./003-timer-contract.md) и [Контракту безопасности](./008-security-contract.md).

## 1. Базовое архитектурное решение персистентности

В рамках DEC-002 долговременное хранение реализуется строго по схеме:

**ВЕРСИОНИРОВАННЫЕ СНИМКИ В ФОРМАТЕ UTF-8 JSON + АТОМАРНОЕ ЗАМЕЩЕНИЕ ФАЙЛОВ В ТОМ ЖЕ КАТАЛОГЕ WINDOWS (SAME-DIRECTORY ATOMIC FILE REPLACEMENT)**.

Система **КАТЕГОРИЧЕСКИ НЕ ИСПОЛЬЗУЕТ** в DEC-002:
* СУБД SQLite или иные встраиваемые базы данных;
* архитектуру журналов транзакций (WAL / Transaction Log / Append-only log);
* форматы TOML или YAML для динамического состояния среды исполнения;
* бинарные форматы сериализации (bincode, postcard и др.);
* кастомные бинарные форматы баз данных.

> [!NOTE]
> Настоящее нормативное решение не авторизует автоматическое добавление зависимостей (`serde`, `serde_json`, Windows API bindings и др.). Авторизация зависимостей и реализация кода производятся на последующих изолированных этапах управления.

## 2. Размещение файлов и модель безопасности (Persistent Root & DACL)

1. **Каталог размещения**:
   * Все персистентные файлы и их временные файлы замещения размещаются строго в защищенном системном корневом каталоге:
     `%ProgramData%\Palka`
2. **Модель безопасности файловой системы (Restricted Allow-List DACL)**:
   * Корневой каталог данных и все создаваемые файлы ДОЛЖНЫ (SHALL) настраиваться с защищенным списком контроля доступа (DACL) на основе строгого разрешающего белого списка (Allow-list):
     * `NT AUTHORITY\SYSTEM`: Полный доступ (Full Control / Allow);
     * `BUILTIN\Administrators`: Полный доступ (Full Control / Allow);
     * `Child SID` / Обычные стандартные пользователи Windows: **Отсутствие любых разрешающих ACE (No Access)**.
   * **Правило запрета доступа**: Доступ стандартным пользователям блокируется в силу **отсутствия разрешающих ACE (Allow ACE)** в DACL, а не путем явного широкого запрета (Deny ACE) для `BUILTIN\Users` или `Everyone`.
   * **Защита от наследования**: Каталог данных настраивается с отключением наследования родительских разрешающих прав файловой системы (Protected DACL), исключая предоставление прав стандартным пользователям.

## 3. Точная каноническая раскладка файлов (Canonical File Layout)

В системе определены ровно **три канонических персистентных файла**:

1. `%ProgramData%\Palka\config.json` — статическая конфигурация службы;
2. `%ProgramData%\Palka\credentials.json` — защищенный контейнер учетных данных;
3. `%ProgramData%\Palka\state.json` — единый авторитарный снимок динамического состояния.

### Временные файлы замещения
* Временные файлы, создаваемые в процессе атомарного замещения, **НЕ ЯВЛЯЮТСЯ** каноническим состоянием.
* Временные файлы создаются строго в том же каталоге (`%ProgramData%\Palka`) с уникальными именами по концептуальной схеме:
  * `.<target-name>.<unique-id>.tmp` (например, `.state.json.<uuid>.tmp`, `.config.json.<uuid>.tmp`, `.credentials.json.<uuid>.tmp`).
* Временные файлы ни при каких условиях не признаются авторитарными и подлежат удалению как устаревшие после успешной валидации канонических файлов.
* Создание иных канонических файлов (например, `state.db`, `timers.json`, `journal.log`, `messages.db`) запрещено.

## 4. Общие правила формата файлов (Common File Format Rules)

Каждый канонический файл SHALL удовлетворять следующим обязательным требованиям:
1. Кодировка: **UTF-8 JSON**.
2. Корневой элемент: **JSON Object**.
3. Обязательное поле версии схемы верхнего уровня:
   ```json
   "schema_version": 1
   ```
4. Значение `schema_version = 1` является **единственной** поддерживаемой версией схемы в DEC-002.
5. **Строгая политика валидации (Strict Schema Policy)**:
   * Все обязательные поля должны присутствовать;
   * Неверные типы данных JSON классифицируются как повреждение;
   * Неизвестные значения enum и некорректно тегированные объекты запрещены;
   * **Неизвестные поля верхнего или вложенного уровня в схеме v1 КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ и приводят к отклонению файла** (silent ignore запрещен);
   * Дубликаты идентификаторов (`TimerId`, `entry_id` в outbox) запрещены.
6. **Запрет скрытого сброса**: Категорически запрещен автоматический деструктивный сброс состояния к значениям по умолчанию для инициализированной установки.
7. Автоматическая миграция схем в DEC-002 не предусмотрена и требует отдельного решения.

## 5. Спецификация `config.json` (Service Configuration)

Файл `config.json` хранит статическую конфигурацию службы, неизменяемую во время стандартных тактов таймеров.

### Концептуальная схема:
```json
{
  "schema_version": 1,
  "child_sid": "S-1-5-21-...",
  "telegram_allowed_user_ids": [123456789],
  "telegram_allowed_chat_ids": [-1001234567890],
  "heartbeat_interval_seconds": 60
}
```

### Инварианты:
* Ровно один сконфигурированный `Child SID`.
* Персистированный белый список `UserId` Telegram.
* Персистированный белый список `ChatId` Telegram.
* Интервал отправки периодических heartbeat-сообщений.
* **Запрет волатильных данных**: Файл `config.json` **НЕ ДОЛЖЕН** содержать состояние таймеров, наблюдаемое состояние сети, `ServiceHealth` или IPC-токены авторизации/сессий.

## 6. Спецификация `credentials.json` (Protected Credentials)

Файл `credentials.json` содержит секретные материалы аутентификации в защищенном виде.

### Концептуальная схема:
```json
{
  "schema_version": 1,
  "pin_hash": "$argon2id$v=19$m=65536,t=3,p=4$...",
  "telegram_bot_token_dpapi": "AQAAANCMnd8BFdERjHoAwE..."
}
```

### Инварианты безопасности:
1. **PIN-код**:
   * Открытый текст PIN-кода **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** сохранять на диск.
   * `pin_hash` содержит хэш-строку Argon2id в формате PHC string, включающую параметры алгоритма, соль и хэш.
   * Никакие попытки ввода PIN не записываются в файл.
2. **Токен Telegram Bot API**:
   * В DEC-002 токен защищается с помощью **Windows DPAPI** (`CryptProtectData`).
   * На диск сохраняется закодированное в Base64 (без переносов строк) представление защищенного DPAPI-блока (`telegram_bot_token_dpapi`).
   * Открытый токен Telegram Bot API **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** сохранять на диск.
   * Строгий DACL файловой системы действует как обязательный эшелон защиты поверх DPAPI.
3. Собственные ключи шифрования Palka или нестандартные криптографические форматы не используются.

## 7. Спецификация `state.json` (Single Authoritative Mutable Snapshot)

Файл `state.json` является **ЕДИНСТВЕННЫМ** авторитарным снимком изменяемого состояния системы. Все взаимосвязанные сущности динамического состояния объединены в одном файле для обеспечения их синхронной атомарной фиксации.

### Концептуальная схема:
```json
{
  "schema_version": 1,
  "desired_internet_state": "Blocked",
  "active_actions": [
    {
      "id": "018f3a5b6c7d8e9f0a1b2c3d4e5f6071",
      "action_kind": "BlockInternet",
      "deadline": 1700000000000,
      "created_at": 1699996400000,
      "created_by": {
        "kind": "ParentTelegram",
        "user_id": 123456789
      },
      "emitted_thresholds": ["M60", "M30"],
      "execution_state": {
        "kind": "Pending"
      }
    }
  ],
  "internet_retry": {
    "attempt_count": 1,
    "last_error": "WFP call failed"
  },
  "telegram_outbox": [
    {
      "entry_id": "018f3a5b6c7d8e9f0a1b2c3d4e5f6081",
      "payload": {
        "kind": "Chat",
        "message": {
          "id": "018f3a5b6c7d8e9f0a1b2c3d4e5f6072",
          "sender": "Child",
          "text": "Я сделал уроки, можно поиграть?",
          "timestamp": 1700000000000,
          "delivery_status": "AcceptedByService"
        }
      },
      "attempt_count": 0,
      "last_error": null
    },
    {
      "entry_id": "018f3a5b6c7d8e9f0a1b2c3d4e5f6082",
      "payload": {
        "kind": "ServiceNotification",
        "text": "Интернет заблокирован по дедлайну таймера."
      },
      "attempt_count": 0,
      "last_error": null
    }
  ]
}
```

### 7.1. Персистируемый состав `state.json`
1. **`desired_internet_state`**: Авторитарная целевая политика доступа (`Unrestricted` или `Blocked`).
2. **`active_actions`**: Список активных запланированных действий со всеми доменными полями (`TimerId`, `ActionKind`, `Deadline`, `created_at`, `created_by`, `emitted_thresholds`, `execution_state`).
3. **`internet_retry`**: Метаданные повторных попыток согласования целевой политики Интернета (`null` либо объект с `attempt_count` и `last_error`).
4. **`telegram_outbox`**: Долговременная очередь исходящих сообщений и системных оповещений в Telegram.

### 7.2. Волатильные данные, КАТЕГОРИЧЕСКИ ЗАПРЕЩЕННЫЕ к сохранению в `state.json`
В `state.json` запрещено сохранять следующие переходные и аппаратно-зависимые состояния:
* Наблюдаемое состояние сети (`InternetState` / `observed_internet_state`);
* Переходный статус питания `ShutdownState::InProgress`;
* `ServiceHealth` как авторитарное состояние восстановления;
* Метрики времени работы процесса (`uptime_seconds`);
* Количество активных сессий трея (`active_tray_sessions`);
* Этап жизненного цикла службы (`ServiceLifecycleStage`);
* Состояние IPC-соединений и маркеры/токены авторизации сессий;
* Монотонные временные метки (`std::time::Instant`);
* Дескрипторы ОС Windows (Named Pipe, файловые дескрипторы, процессы);
* Объекты адаптеров платформы;
* Состояние процессов трея;
* Временные счетчики попыток ввода PIN и блокировок;
* Открытый PIN и открытый токен Telegram.

Все указанные сущности служба реконструирует или повторно опрашивает при запуске. Фактическое состояние сети `InternetState` **всегда** перепроверяется через `InternetGate::current_state(...)`.

## 8. Точное представление типов в JSON v1 (Wire Representation)

В схеме v1 для всех персистируемых доменных типов зафиксированы следующие точные строковые и тегированные представления:

1. **`DesiredInternetState`**:
   * `"Unrestricted"`
   * `"Blocked"`
2. **`ActionKind`**:
   * `"BlockInternet"`
   * `"ShutdownComputer"`
3. **`WarningThreshold`**:
   * `"M60"`, `"M30"`, `"M20"`, `"M10"`, `"M3"`
4. **`Initiator`** (тегированный объект):
   * `ParentLocalPin`: `{"kind": "ParentLocalPin"}`
   * `ParentTelegram`: `{"kind": "ParentTelegram", "user_id": 123456789}`
5. **`ActionExecutionState`** (тегированный объект):
   * `Pending`: `{"kind": "Pending"}`
   * `Executing`: `{"kind": "Executing"}`
   * `Failed`: `{"kind": "Failed", "reason": "строка ошибки"}`
6. **`TimerId` и `MessageId`**:
   * Каноническая 32-символьная шестнадцатеричная строка в нижнем регистре (`[0-9a-f]{32}`).
7. **`UtcDateTime` и `Deadline`**:
   * Знаковое целое число в формате JSON (Unix timestamp в миллисекундах UTC, `i64`). Числа с плавающей точкой и локализованные строки дат запрещены.

## 9. Допустимые состояния действий на диске (Persisted Action States)

В коллекции `active_actions` персистентного файла `state.json` допускаются **ТОЛЬКО** следующие состояния `ActionExecutionState`:
1. `Pending`
2. `Executing`
3. `Failed { reason }`

### Семантика состояния `Executing` и окна сбоев:
Состояние `Executing` означает:
* Наступил дедлайн запланированного действия (`remaining <= 0`);
* Служба пересекла границу долговременной передачи на исполнение и зафиксировала это в `state.json`;
* Действие более не подлежит отмене;
* Долговременное состояние фиксирует обязательство исполнения/нахождение в процессе исполнения;
* Платформенный вызов **еще может быть не вызван** (сбой до вызова платформы), **может выполняться в данный момент** (сбой во время вызова) либо **уже вернул управление, но его терминальный исход еще не зафиксирован на диске** (сбой до фиксации).
Состояние `Executing` **НЕ означает** физический успех на платформе, подтверждение сетевого шлюза или фактическое выключение питания.

### Правило терминальных состояний:
* Состояния `Completed` и `Missed` являются **терминальными** исходами и **НЕ ДОЛЖНЫ** оставаться в `active_actions` на диске в зафиксированном снимке.
* При переходе действия в `Completed` или `Missed` его удаление из `active_actions` производится в рамках той же атомарной транзакции записи `state.json`, которая фиксирует сопутствующие изменения (например, постановку уведомления в `telegram_outbox`).
* Действие `BlockInternet` или `ShutdownComputer` в состоянии `Failed` **НЕ удаляется** с диска молчаливо, а сохраняется в `active_actions`.

### Инвариант уникальности `TimerId`:
* Каждый `TimerId` в `active_actions` обязан быть уникальным. При обнаружении дубликата `TimerId` снимок считается поврежденным (автоматическая дедупликация запрещена).

## 10. Метаданные повторных попыток Интернета (`internet_retry`)

* `internet_retry` содержит метаданные фонового согласования (`attempt_count`, `last_error`).
* `internet_retry` **не подменяет** и **не дублирует** `desired_internet_state`.
* При наличии `internet_retry` на момент старта служба возобновляет попытки согласования платформы с целевым `desired_internet_state`.
* Алгоритм экспоненциальной задержки и конкретный переход `Failed -> Executing` определяются последующими сервисными контрактами.

## 11. Долговременная очередь Telegram (`telegram_outbox`)

1. **Конверт очереди и разделение полезной нагрузки**:
   * Каждый элемент очереди `telegram_outbox` является отдельной единицей транспортной работы со следующим конвертом:
     ```json
     {
       "entry_id": "018f3a5b6c7d8e9f0a1b2c3d4e5f6081",
       "payload": { ... },
       "attempt_count": 0,
       "last_error": null
     }
     ```
   * **`entry_id`**: 128-битный сервисный идентификатор элемента очереди, закодированный строго как 32-символьная hex-строка в нижнем регистре (`[0-9a-f]{32}`). Является уникальным в пределах `telegram_outbox`.
   * Поле `payload` имеет ровно два тегированных варианта:
     1. **`Chat`**:
        ```json
        {
          "kind": "Chat",
          "message": {
            "id": "018f3a5b6c7d8e9f0a1b2c3d4e5f6072",
            "sender": "Child",
            "text": "Текст сообщения",
            "timestamp": 1700000000000,
            "delivery_status": "AcceptedByService"
          }
        }
        ```
        *Правило маршрутизации чата в `telegram_outbox`*: Поле `sender` в сообщении внутри `telegram_outbox` принимает **СТРОГО значение `"Child"`** (исходящие сообщения от ребенка родителям в Telegram). Значение `"sender": "Parent"` внутри `telegram_outbox` **недопустимо**, поскольку сообщения родителей направляются по IPC в трей ребенка и не помещаются обратно в очередь Telegram. Значения `"Service"`, `"System"`, `"Bot"` категорически запрещены. Статус `delivery_status` внутри персистентной очереди обязан быть **строго `"AcceptedByService"`**.
     2. **`ServiceNotification`**:
        ```json
        {
          "kind": "ServiceNotification",
          "text": "Текст системного оповещения"
        }
        ```
        Не содержит полей `sender`, `message` или `delivery_status`. Присутствие в зафиксированном снимке `state.json` удостоверяет принятие оповещения службой.
2. **Штатный порядок доставки и удаление по Ack (Durable-Outbox-First)**:
   * Элемент очереди помещается в `telegram_outbox` внутри `state.json` и надежно фиксируется на диске ДО начала сетевой передачи.
   * После фиксации инициируется сетевой запрос к Telegram Bot API.
   * После получения подтверждения об успешном приеме (`HTTP 200 OK`) запись удаляется из `telegram_outbox` **строго по ее уникальному `entry_id`** в следующем атомарном обновлении `state.json`.
   * Удаление по совпадению текста, позиции в массиве или временной метке категорически запрещено. Две записи `ServiceNotification` с одинаковым текстом, но разными `entry_id` являются независимыми.
   * Обеспечивается гарантия **at-least-once delivery** (возможна повторная отправка при сбое процесса до фиксации удаления, потеря исключена).

## 12. Протокол атомарного замещения файлов (Atomic Replacement Protocol)

Все обновления любого из трех канонических файлов (`state.json`, `config.json`, `credentials.json`) выполняются строго по следующему протоколу:

1. В памяти формируется и полностью валидируется новое представление JSON.
2. Создается уникальный временный файл в **ТОМ ЖЕ** каталоге (`%ProgramData%\Palka`), что и целевой файл.
3. Полный массив байтов записывается во временный файл.
4. Выполняется принудительный сброс дисковых буферов на стабильный накопитель (`FlushFileBuffers` / write-through).
5. Производится атомарная публикация файла:
   * При замене существующего файла используется `ReplaceFileW` (или эквивалентный примитив атомарного замещения на одном томе Windows);
   * При первичной публикации используется атомарное переименование/перемещение `MoveFileExW` с флагом `MOVEFILE_WRITE_THROUGH`.
6. Только после успешного завершения шага 5 состояние считается авторитарным.

### Категорически запрещено:
* Изменять канонический файл по месту с усечением (`truncate and overwrite`);
* Удалять старый канонический файл до успешного сброса нового файла на диск;
* Копировать файл поверх старого неатомарной цепочкой операций;
* Признавать неподтвержденный временный файл авторитарным состоянием;
* Подтверждать клиентские команды до завершения атомарной фиксации их последствий.

## 13. Восстановление при наличии устаревших временных файлов

* При старте службы авторитарными признаются **только** канонические файлы (`config.json`, `credentials.json`, `state.json`).
* Наличие оставшихся от предыдущих сбоев файлов `.tmp` **НЕ приводит** к их автоматическому переименованию в канонические.
* Правило «выигрывает файл с более свежей датой» категорически запрещено.
* Устаревшие временные файлы могут быть удалены службой только после успешной загрузки и валидации канонических файлов.

## 14. Политика инициализации и отсутствия файлов

1. Процедура установки/первичной настройки Palka обязана создать валидные исходные файлы `config.json`, `credentials.json` и `state.json` до включения службы.
2. После инициализации отсутствие любого из трех канонических файлов рассматривается как **нарушение целостности хранилища (Critical Corruption)**.
3. Служба **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНА** автоматически создавать отсутствующий `state.json` с разрешающими значениями по умолчанию (`DesiredInternetState::Unrestricted`).

## 15. Политика обработки повреждений и аварийных ситуаций (Corruption Policy)

Если какой-либо обязательный канонический файл отсутствует после инициализации, синтаксически поврежден, имеет неподдерживаемую версию схемы или нарушает кросс-полевые инварианты:
* Служба фиксирует сбой подсистемы персистентности;
* Интегральный статус здоровья переводится в `HealthStatus::Critical`;
* **Событие `ServiceReady` КАТЕГОРИЧЕСКИ НЕ ЭМИТИРУЕТСЯ**, служба отказывается декларировать готовность;
* Событие об ошибке регистрируется в системном журнале Windows Event Log;
* Запрещены автоматический сброс к заводским настройкам, очистка таймеров или скрытое понижение версии схемы.

### Исключение: Экстренное оповещение при сбое персистентности
Если `state.json` недоступен или поврежден, но `config.json` и `credentials.json` валидны и токен Telegram может быть расшифрован:
* Служба предпринимает попытку прямого экстренного оповещения родителю в Telegram о критическом сбое хранилища в обход недоступного `telegram_outbox`;
* Экстренное оповещение носит характер best-effort, не персистируется и не предоставляет гарантий доставки;
* Использование экстренного пути для обычных операций категорически запрещено.

## 16. Порядок фиксации операций таймеров и политик

### 16.1. Создание таймера (`ScheduleInternetBlock`, `ScheduleShutdown`)
1. Служба валидирует и авторизует команду.
2. Создается структура `ScheduledAction` в состоянии `Pending`.
3. Пороги, уже пройденные на момент создания, заносятся в `emitted_thresholds`.
4. Производится атомарная запись обновленного `state.json`.
5. Только **ПОСЛЕ** успешной фиксации на диске команда подтверждается клиенту.
6. Если длительность таймера в точности равна порогу предупреждения, такое предупреждение становится доступным к генерации только после успешной фиксации снимка.

### 16.2. Отмена таймера (`CancelShutdownTimer`, `CancelInternetBlockTimer`)
1. Действие удаляется из предлагаемого снимка состояния.
2. Производится атомарная фиксация `state.json`.
3. Только после фиксации клиенту подтверждается отмена.
4. Для `ShutdownComputer` отмена допускается только при `current_remaining_seconds > 0`.

### 16.3. Фиксация предупреждений
* При наступлении порога предупреждения соответствующий `WarningThreshold` добавляется в `emitted_thresholds` действия.
* Обновленные `emitted_thresholds` и исходящее сообщение `ServiceNotification` (с уникальным `entry_id`) в `telegram_outbox` фиксируются в рамках **ЕДИНОГО** снимка `state.json`.

### 16.4. Наступление дедлайна блокировки Интернета
* При наступлении дедлайна запланированной блокировки (`remaining <= 0`) служба **ДО** вызова драйвера `InternetGate` обязана атомарно зафиксировать в `state.json`:
  * `execution_state = Executing`;
  * `desired_internet_state = Blocked`.
* Только после успешного обновления `state.json` вызывается `InternetGate::block_internet`.
* Если служба аварийно завершится до вызова платформы, восстановление при старте увидит целевой `DesiredInternetState::Blocked` и применит блокировку.

### 16.5. Наступление дедлайна выключения компьютера (Runtime Shutdown Execution)
* При наступлении дедлайна выключения (`remaining <= 0`) служба:
  1. Переводит действие `Pending` в `Executing`.
  2. Атомарно фиксирует `execution_state = Executing` в `state.json`. Действие **НЕ удаляется** из `active_actions` до завершения платформенного вызова.
  3. Вызывает платформенный шлюз `PowerController::initiate_shutdown()`.
  4. **При успешном ответе платформы (`Ok(())`)**:
     * Запрос принят ОС Windows;
     * Действие переходит в терминальное состояние `Completed`;
     * Волатильный статус переводится в `ShutdownState::InProgress` (не сохраняется на диск);
     * Служба атомарно фиксирует обновленный `state.json`, удаляя терминальное действие из `active_actions`.
  5. **При ошибке платформы (`Err(PowerError)`)**:
     * Действие переходит в `ActionExecutionState::Failed { reason }`;
     * Состояние `Failed` атомарно фиксируется в `state.json` с сохранением действия в `active_actions`;
     * Статус `ShutdownState::InProgress` не устанавливается.

### 16.6. Немедленная блокировка (`ImmediateInternetBlock`)
* До вызова `InternetGate::block_internet` в `state.json` атомарно фиксируется `desired_internet_state = Blocked`.
* Действие `ScheduledAction` не создается.

### 16.7. Снятие блокировки (`RestoreInternet`)
* До вызова `InternetGate::unblock_internet` в `state.json` атомарно фиксируется `desired_internet_state = Unrestricted`.
* Действие `ScheduledAction` не создается.
* В случае сбоя платформы `desired_internet_state` **НЕ откатывается** в `Blocked`.

### 16.8. Успешное исполнение блокировки Интернета
* После физического подтверждения от `InternetGate::current_state == Blocked` действие `ScheduledAction` удаляется из `active_actions`, а метаданные `internet_retry` очищаются в следующем снимке `state.json`.

### 16.9. Сбой исполнения блокировки Интернета
* При сбое вызова `InternetGate` в `state.json` фиксируются:
  * `desired_internet_state = Blocked`;
  * `execution_state = Failed { reason }` (для запланированного действия);
  * метаданные `internet_retry`.

## 17. Процедура восстановления при старте службы (Startup Recovery)

После успешной загрузки и валидации `state.json`:

1. **Восстановление сетевой политики**:
   * Служба безусловно согласует платформу с сохраненным `desired_internet_state`.
   * Сохраненное в прошлом `InternetState` не считывается с диска и опрашивается заново через `InternetGate::current_state`.
   * Просроченное действие `BlockInternet` в состоянии `Pending` переводится в `Executing` и передается на согласование в сторону `Blocked`.
   * Для действия `BlockInternet` в состоянии `Executing` или `Failed` процесс согласования возобновляется.
2. **Восстановление таймеров выключения компьютера**:
   * Для **ЛЮБОГО** активного действия `ShutdownComputer` на диске (`Pending`, `Executing` или `Failed`), чей дедлайн на момент старта службы уже наступил (`remaining <= 0`), служба **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНА** вызывать `PowerController::initiate_shutdown` (запрет повторного выключения свежезагруженной ОС).
   * Сохраненное состояние `Executing` может являться следствием сбоя до вызова платформы, сбоя во время вызова или сбоя после `Ok(())` до публикации удаления — служба не пытается разделять эти случаи и безусловно применяет безопасный сценарий:
     * действие классифицируется как пропущенный дедлайн (`Missed`);
     * действие удаляется из `active_actions`;
     * волатильный статус питания устанавливается в `ShutdownState::Idle`;
     * в очередь `telegram_outbox` помещается уведомление родителям `MissedDeadlineOccurred` (как `ServiceNotification` с уникальным `entry_id`);
     * снимок `state.json` атомарно фиксируется.
   * Для действия `ShutdownComputer` с дедлайном в будущем (`remaining > 0`) таймер восстанавливается с регистрацией пройденных порогов в `emitted_thresholds`.

## 18. Отсутствие межфайловых транзакций

* Обновления файлов `config.json`, `credentials.json` и `state.json` являются независимыми атомарными операциями.
* Межфайловые транзакции файловой системы Windows не заявляются и не используются.
* Все взаимосвязанные динамические сущности жизненного цикла размещаются строго внутри единого файла `state.json`.
