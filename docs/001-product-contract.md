# Продуктовый контракт (Product Contract)

Документ устанавливает нормативные продуктовые требования к системе родительского контроля.

## 1. Функциональные требования (Functional Requirements)

1. **Запланированная блокировка Интернета (Scheduled Internet Blocking)**:
   * Система ДОЛЖНА (SHALL) поддерживать установку таймера на блокировку доступа к сети Интернет для одного сконфигурированного пользователя Windows.
   * Система ДОЛЖНА (SHALL) поддерживать немедленную ручную блокировку и немедленную ручную разблокировку (восстановление) доступа к сети Интернет.

2. **Запланированное выключение компьютера (Scheduled Computer Shutdown)**:
   * Система ДОЛЖНА (SHALL) поддерживать установку таймера на завершение работы операционной системы Windows (выключение питания).
   * Система ДОЛЖНА (SHALL) поддерживать отмену запланированного таймера выключения.

3. **Предупредительные уведомления (Warning Notifications)**:
   * Система ДОЛЖНА (SHALL) формировать предупредительные события перед исполнением действия (блокировка Интернета или выключение компьютера) строго на следующих временных порогах до наступления дедлайна:
     * **60 минут**
     * **30 минут**
     * **20 минут**
     * **10 минут**
     * **3 минуты**
   * Если создаваемый или восстанавливаемый таймер имеет длительность меньше определенного порога, уже пройденные пороги НЕ ДОЛЖНЫ (SHALL NOT) генерироваться или отправляться.

4. **Селективность блокировки сети (Network Gate Selectivity)**:
   * Блокировка доступа к сети Интернет ДОЛЖНА (SHALL) таргетироваться исключительно на SID (Security Identifier) сконфигурированного пользователя Windows.
   * Блокировка сети НЕ ДОЛЖНА (SHALL NOT) намеренно ограничивать сетевую связность для самой привилегированной службы Windows (`service`), обеспечивая бесперебойную связь службы с Telegram Bot API.

5. **Живучесть и персистентность таймеров (Timer Durability)**:
   * Запланированные действия и их дедлайны ДОЛЖНЫ (SHALL) сохраняться и сохранять корректность при следующих событиях:
     * завершение или аварийное падение процесса трея (`tray`);
     * выход пользователя из сессии (logout / sign-out);
     * перезапуск службы (`service`);
     * перезагрузка компьютера (reboot / cold restart).

6. **Возможности трей-приложения (Tray Application Capabilities)**:
   * Приложение в трее (`tray`) ДОЛЖНО (SHALL) обеспечивать:
     * отображение текущего состояния системы (статус сети, активные таймеры, состояние службы);
     * вывод локальных всплывающих уведомлений о предупреждениях и сообщениях;
     * интерфейс двустороннего текстового чата «родитель — ребенок»;
     * защищенный PIN-кодом ввод для выполнения административных действий на локальной машине.

7. **Авторитетность проверки PIN-кода (Authoritative PIN Verification)**:
   * Проверка корректности PIN-кода ДОЛЖНА (SHALL) производиться исключительно и авторитарно внутри компонента `service`.
   * Компонент `tray` НЕ ДОЛЖЕН (SHALL NOT) производить локальную валидацию PIN-кода и не должен хранить секреты или мастер-пароли.

8. **Удаленное управление через Telegram (Telegram Remote Control)**:
   * Telegram-адаптер службы ДОЛЖЕН (SHALL) поддерживать следующие строго определенные удаленные операции:
     * запрос текущего статуса системы (Status Query);
     * планирование блокировки Интернета (Internet Block Scheduling);
     * восстановление доступа к Интернету / отмена блокировки (Internet Restoration);
     * отмена таймера блокировки Интернета (Internet Timer Cancellation);
     * планирование выключения компьютера (Shutdown Scheduling);
     * отмена таймера выключения компьютера (Shutdown Timer Cancellation);
     * отправка сообщений от родителя ребенку (Parent-to-Child Messages).

9. **Маршрутизация сообщений чата (Chat Routing)**:
   * Сообщения от ребенка родителю ДОЛЖНЫ (SHALL) передаваться из интерфейса `tray` через IPC в `service`, а затем отправляться службой в сконфигурированный Telegram-чат.
   * Сообщения от родителя ребенку ДОЛЖНЫ (SHALL) приниматься службой из Telegram и доставляться через IPC в `tray` для отображения ребенку.

10. **Ограничение доступа к Telegram (Telegram Authorization Restriction)**:
    * Доступ к управлению через Telegram ДОЛЖЕН (SHALL) быть ограничен исключительно явно сконфигурированным списком идентификаторов пользователей и чатов (Allowed User/Chat IDs).
    * Любые запросы от неавторизованных идентификаторов ДОЛЖНЫ (SHALL) отклоняться и игнорироваться.

11. **Запрет произвольного удаленного исполнения (No Arbitrary Execution)**:
    * Интеграция с Telegram ДОЛЖНА (SHALL) предоставлять строго замкнутый набор доменных команд.
    * Категорически ЗАПРЕЩАЕТСЯ (SHALL NOT) наличие функциональности произвольного удаленного исполнения команд (arbitrary remote command execution), запуска shell/PowerShell-скриптов, запуска исполняемых файлов или запуска произвольных системных процессов.

12. **Автономность принудительного исполнения (Enforcement Independence)**:
    * Исполнение блокировки Интернета и выключения компьютера ДОЛЖНО (SHALL) непрерывно функционировать при отсутствии или принудительном завершении процесса `tray`.

## 2. Ролевая модель и предположения о среде (Environment Assumptions)

* **Учетная запись родителя (Parent Account)**: Подразумевается учетная запись с правами Администратора Windows (Windows Administrator).
* **Учетная запись ребенка (Child Account)**: Подразумевается стандартная учетная запись Windows (Windows Standard User).
* **Границы ответственности безопасности**:
  * Стандартный пользователь (ребенок) НЕ ДОЛЖЕН (SHALL NOT) иметь возможности остановить службу, изменить конфигурационные файлы службы или обойти фильтрацию трафика.
  * Абсолютная защита от локального администратора Windows (родителя) явно находится вне рамок проекта (Out of Scope).
