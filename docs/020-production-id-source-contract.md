# Нормативный контракт производственного источника идентификаторов (Production IdSource Contract V1)

Настоящий документ устанавливает нормативные требования, архитектурное разделение обязанностей, модель энтропии, семантику обработки отказов и матрицу верификации для производственной реализации абстракции генератора идентификаторов `IdSource` в системе PALKA.

Настоящий документ представляет собой рабочий нормативный контракт этапа документирования (`PRODUCTION-ID-SOURCE DOCUMENTATION`). Сама зависимость `IdSource` в рамках данного документа **НЕ СТАНОВИТСЯ ГОТОВОЙ** (`PRODUCTION_ID_SOURCE_STATUS: DOCUMENTED_LOCALLY_PENDING_AUDIT`).

## 2. Неизменяемый контракт рантайма (Frozen Runtime Trait Input)

### 2.1. Точная сигнатура трейта
В кодовой базе службы (`crates/service/src/runtime.rs:98-101`) нормативно зафиксирован и неизменен интерфейс порта генератора идентификаторов:
```rust
pub trait IdSource: Send + Sync {
    fn next_timer_id(&self) -> TimerId;
    fn next_outbox_id(&self) -> OutboxEntryId;
}
```

### 2.2. Запрет на модификацию существующего контракта
```text
CURRENT_ID_SOURCE_TRAIT_CHANGE_REQUIRED: NO
RUNTIME_RS_CHANGE_REQUIRED: NO
```
1. Производственная реализация **ОБЯЗАНА** полностью соответствовать данному непогрешимому (infallible) трейту.
2. Методы `next_timer_id()` и `next_outbox_id()` **КАТЕГОРИЧЕСКИ НЕ ИМЕЮТ ПРАВА** выполнять поштучные (per-call) фаллибельные обращения к генераторам случайных чисел операционной системы (ОС CSPRNG).
3. При генерации идентификаторов **СТРОЖАЙШЕ ЗАПРЕЩЕНО (FORBIDDEN)**:
   * Вызывать панику (`panic!`);
   * Использовать `unwrap()` или `expect()` на результатах вызовов функций ОС;
   * Фабриковать нулевой/дефолтный идентификатор (`[0; 16]`) в случае сбоя генерации;
   * Использовать псевдослучайный фоллбэк на базе системного времени (timestamp);
   * Использовать идентификатор процесса (PID) или дескрипторы потоков;
   * Использовать MAC-адрес сетевого адаптера или статический GUID машины;
   * Использовать фиксированные детерминированные константы в производственном коде;
   * Использовать слабый инкрементный счетчик, инициализированный без криптографического сида.

## 3. Доменная семантика идентификаторов (Identifier Domain Semantics)

### 3.1. Представление типов
```text
TimerId:        palka_core::TimerId([u8; 16])
OutboxEntryId:  palka_service::persistence::OutboxEntryId([u8; 16])
TIMER_ID_BITS:  128
OUTBOX_ID_BITS: 128
```
* `TimerId` (определен в `crates/core/src/lib.rs:17`) — непрозрачный 128-битный идентификатор запланированных действий таймера (`ScheduledAction`).
* `OutboxEntryId` (определен в `crates/service/src/persistence.rs:16`) — уникальный 128-битный идентификатор записи исходящей очереди Telegram (`TelegramOutboxEntry`).

### 3.2. Отсутствие семантики UUID (RFC 4122)
```text
UUID_SEMANTICS:         NO
RFC4122_VERSION_BITS:   NOT_REQUIRED
RFC4122_VARIANT_BITS:   NOT_REQUIRED
OPAQUE_IDENTIFIER:      YES
```
Доменная модель PALKA и подсистема персистентности трактуют оба идентификатора исключительно как непрозрачные 16-байтовые массивы (`[u8; 16]`). Специфические биты версий и вариантов стандарта RFC 4122 (UUID v4) не требуются и нормативно не инспектируются.

### 3.3. Допустимость нулевых значений в домене и запрет фоллбэка
```text
ALL_ZERO_DOMAIN_VALUE_ALLOWED:    YES
PRODUCTION_ZERO_FAILURE_FALLBACK: FORBIDDEN
```
Тип `[u8; 16]` чисто теоретически допускает значение из 16 нулевых байт. Однако использование нулевого значения как суррогата «заглушки при сбое» в производственном источнике идентификаторов **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО**.

### 3.4. Сериализация в персистентном хранилище
Сериализация обоих типов строго подчиняется требованиям [docs/009-persistence-contract.md](009-persistence-contract.md):
* Ровно 32 символа в шестнадцатеричном формате в нижнем регистре (`[0-9a-f]{32}`);
* Использование дефисов, пробелов или прописных букв безусловно отвергается валидатором `parse_128bit_id_hex`.

## 4. Каноническая производственная модель генерации (Canonical Production Model)

### 4.1. Утвержденная модель V1
В качестве канонической модели жизненного цикла V1 утверждается:
```text
MODEL:
FALLIBLE_RANDOM_SEED_CONSTRUCTION_PLUS_INFALLIBLE_LOCAL_128BIT_SEQUENCE
```

### 4.2. Источник системной энтропии и флаги Win32
* **Канонический системный вызов**: Windows Cryptography Next Generation (CNG) `BCryptGenRandom`.
* **Нормативный флаг**: `BCRYPT_USE_SYSTEM_PREFERRED_RNG`.
* **Точная проекция в `windows` 0.62.2**:
```rust
pub unsafe fn BCryptGenRandom(
    halgorithm: Option<BCRYPT_ALG_HANDLE>,
    pbbuffer: &mut [u8],
    dwflags: BCRYPTGENRANDOM_FLAGS,
) -> NTSTATUS;
```

### 4.3. Семантика получения начального сида
1. Выделяется буфер ровно в 16 байт (`[u8; 16]`).
2. Функция `BCryptGenRandom` вызывается **РОВНО ОДИН РАЗ** в процессе конструирования производственного объекта.
3. Параметр `halgorithm` **ОБЯЗАН** передаваться как `None` (NULL).
4. Параметр `dwflags` **ОБЯЗАН** содержать строго флаг `BCRYPT_USE_SYSTEM_PREFERRED_RNG`.
5. Возвращенные 16 байт становятся фактическим исходным состоянием локальной последовательности.
6. Данный вызов **НЕ ЯВЛЯЕТСЯ ТЕСТОВЫМ ПРОБИРОВАНИЕМ (NOT A PROBE)**: полученные байты образуют основу рабочего генератора.

```text
OS_RANDOM_CALL_FREQUENCY:          CONSTRUCTION_ONLY
POST_CONSTRUCTION_OS_RANDOM_CALLS: ZERO
```

### 4.4. Отказ от альтернативных механизмов
Использование RPC-функции `UuidCreate` или сторонних крейтов (`uuid`, `rand`, `getrandom`) в качестве канонического генератора V1 **ОТВЕРГНУТО**.

## 5. Семантика обработки системных отказов (Failure Semantics)

### 5.1. Обработка возвращаемого кода NTSTATUS
Функция `BCryptGenRandom` является фаллибельной на этапе конструирования и возвращает системный код типа `NTSTATUS`.
* В крейте `windows` 0.62.2 тип `NTSTATUS` реализует методы `.is_ok()` и `.is_err()`, предоставляющие каноническую семантику системного макроса Windows `NT_SUCCESS(status)`.
* Возвращаемый код `NTSTATUS` **ОБЯЗАН** проверяться реализацией напрямую через эти методы.
* Вызов `unwrap()` на значении `NTSTATUS` **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕН**.
* Исходное числовое значение системного статуса (`status.0: i32`) **ОБЯЗАНО** сохраняться без искажений при обнаружении сбоя.
* **СТРОЖАЙШЕ ЗАПРЕЩЕНО**:
  * Преобразовывать `NTSTATUS` в искусственный код ошибки Win32 (`GetLastError`);
  * Оборачивать его в `HRESULT`, выдавая за стандартную ошибку Win32;
  * Терять или маскировать числовое значение исходного кода ошибки;
  * Использовать числовые сравнения с нулем в качестве правила классификации успеха/сбоя;
  * Классифицировать значения NTSTATUS вне STATUS_SUCCESS как безусловный сбой (решающим правилом проверки отказа выступает исключительно предикат is_err()).

### 5.2. Таксономия платформенных ошибок
На уровне платформы фиксируется строго типизированное перечисление:
```rust
#[derive(Debug)]
pub enum WindowsIdGeneratorError {
    UnsupportedPlatform,
    RandomSeedGenerationFailure {
        ntstatus: i32,
    },
}
```
Поле `ntstatus` **ОБЯЗАНО** строго хранить точное исходное значение `status.0`.

### 5.3. Нормативное решающее правило конструирования
Нормативное правило проверки результата вызова `BCryptGenRandom` формулируется строго следующим образом:
```rust
let status = unsafe {
    BCryptGenRandom(
        None,
        &mut seed,
        BCRYPT_USE_SYSTEM_PREFERRED_RNG,
    )
};

if status.is_err() {
    return Err(WindowsIdGeneratorError::RandomSeedGenerationFailure {
        ntstatus: status.0,
    });
}
```
* **УСПЕХ (`status.is_ok() == true` / `NT_SUCCESS(status)`)**: конструирование успешно продолжается, возвращается валидный инициализированный экземпляр `WindowsIdSequence`. Значение `STATUS_SUCCESS (0)` является документированным штатным успешным возвратом `BCryptGenRandom`, однако проверка равенства `STATUS_SUCCESS` не является общим контрактом проверки успеха `NTSTATUS`; каноническим предикатом выступает строго `status.is_ok()`.
* **СБОЙ (`status.is_err() == true`)**: возвращается ошибка `WindowsIdGeneratorError::RandomSeedGenerationFailure { ntstatus: status.0 }`. Экземпляр генератора не создается.
* В версии V1 автоматический повтор (`retry`) вызова `BCryptGenRandom` не предусмотрен. Любой сбой получения энтропии при старте службы считается фатальным для процесса инициализации.

## 7. Локальный генератор последовательности (WindowsIdSequence)

### 7.1. Концептуальный интерфейс
```rust
pub struct WindowsIdSequence {
    state: Mutex<u128>,
}

impl WindowsIdSequence {
    pub fn from_production() -> Result<Self, WindowsIdGeneratorError>;
    pub fn next_128(&self) -> [u8; 16];
}
```

### 7.2. Инициализация и алгоритм генерации
1. **Инициализация**: состояние инициализируется из 16-байтового случайного сида как `u128::from_be_bytes(seed)`.
2. **Шаги генерации `next_128(&self)`**:
   * Захват блокировки мьютекса `state.lock()`;
   * При отравлении мьютекса (`PoisonError`) состояние извлекается через `into_inner()` без вызова паники (`MUTEX_POISON_PANIC: FORBIDDEN`);
   * Фиксация текущего значения `u128`;
   * Продвижение состояния вызовом `state.wrapping_add(1)`;
   * Возврат зафиксированного значения в виде байтов `current.to_be_bytes()`.

```text
FIRST_VALUE:              SEED
SEQUENCE_BYTE_ORDER:      BIG_ENDIAN
SEQUENCE_PERIOD:          2^128
OVERFLOW_BEHAVIOR:        WRAPPING
ARITHMETIC_PANIC:         FORBIDDEN
MUTEX_POISON_PANIC:       FORBIDDEN
```

### 7.3. Пределы гарантии уникальности
Контракт гарантирует строгую математическую неповторяемость генерируемых значений внутри одного процесса вплоть до исчерпания полного периода $2^{128}$ шагов. Контракт **НЕ УТВЕРЖДАЕТ** абсолютную пожизненную глобальную уникальность при бесконечных перезапусках службы (уникальность между перезапусками является вероятностной).

### 7.4. Ограничения тестовых швов
Для всестороннего тестирования поведения последовательности (проверка инкремента, переполнения, отравления мьютекса) разрешается реализация вспомогательного конструктора из фиксированного сида:
* Данный конструктор **ОБЯЗАН** быть закрытым для внешнего производственного кода (`pub(crate)`, `#[cfg(test)]` или аналогичный защитный механизм);
* Производственные вызывающие стороны **КАТЕГОРИЧЕСКИ НЕ ИМЕЮТ ПРАВА** подменять вызов `BCryptGenRandom` на фиксированный сид.

## 8. Адаптер службы и резервирование идентификаторов (Service Adapter & Reservation)

### 8.1. Порядок конструирования адаптера
Конструирование адаптера `WindowsIdSourceAdapter` выполняется строго по следующему таймингу:
* **ПОСЛЕ**: успешного завершения процедуры начальной загрузки `bootstrap.bootstrap()` и валидации персистентного состояния `BootstrappedServiceState`;
* **СТРОГО ДО**: передачи зависимостей в конструктор рантайма `ServiceRuntime::start(...)`.

Каноническая концептуальная сигнатура конструктора:
```rust
impl WindowsIdSourceAdapter {
    pub fn from_production(state: &PersistentState) -> Result<Self, PlatformError>;
}
```

### 8.2. Построение набора зарезервированных идентификаторов
При конструировании адаптер выполняет следующие обязательные шаги:
1. Вызывает `WindowsIdSequence::from_production()` для получения рабочего генератора;
2. Извлекает все идентификаторы активных действий из `state.active_actions[*].id.0`;
3. Извлекает все идентификаторы записей исходящей очереди из `state.telegram_outbox[*].entry_id.0`;
4. Объединяет их в единую хеш-таблицу `reserved_ids: HashSet<[u8; 16]>`;
5. Сохраняет сформированное множество в качестве **неизменяемого (immutable)** поля экземпляра адаптера;
6. Возвращает готовый к работе адаптер.

Модификация персистентного состояния при создании адаптера не производится.

### 8.3. Семантика пропуска коллизий (Collision Skip Loop)
Внутренняя генерация идентификатора в адаптере реализуется по схеме:
```rust
fn next_raw_id(&self) -> [u8; 16] {
    loop {
        let candidate = self.sequence.next_128();
        if !self.reserved_ids.contains(&candidate) {
            return candidate;
        }
    }
}
```
* Если очередное значение последовательности совпадает с идентификатором объекта, сохраненного до перезапуска службы, оно **пропускается** и последовательность продвигается дальше.
* Пропуск коллизии гарантированно происходит **ДО** возврата значения в координатор `ServiceRuntime`.

## 9. Обоснование предотвращения коллизий до сохранения в память (Pre-Insertion Prevention Rationale)

### 9.1. Анализ кода рантайма координатора
В методе `commit_post_side_effect_candidate` (`crates/service/src/runtime.rs:609-626`) зафиксирована последовательность действий:
```rust
fn commit_post_side_effect_candidate(
    &mut self,
    candidate: PersistentState,
) -> Result<(), StateStoreError> {
    self.state = candidate.clone(); // <-- МУТАЦИЯ IN-MEMORY СОСТОЯНИЯ ПРОИСХОДИТ ДО ВАЛИДАЦИИ ДИСКА!
    match self.store.save(&candidate) {
        Ok(()) => {
            self.pending_durable_candidate = None;
            self.mark_persistence_success();
            Ok(())
        }
        Err(e) => {
            self.pending_durable_candidate = Some(candidate);
            self.mark_persistence_failure(&e);
            Err(e)
        }
    }
}
```

### 9.2. Архитектурный вывод о недопустимости запоздалого обнаружения коллизий
1. Если бы сгенерированный идентификатор совпал с уже существующим, слой сохранения `store.save(&candidate)` вернул бы ошибку `PersistenceError::DuplicateTimerId` или `PersistenceError::DuplicateOutboxEntryId`.
2. Однако координатор рантайма **УЖЕ ЗАГРЯЗНИЛ БЫ** свое оперативное состояние `self.state`, приняв поврежденного кандидата, и выставил бы `self.pending_durable_candidate`.
3. Следовательно, полагаться на валидаторы персистентности как на штатный механизм обнаружения коллизий **НЕДОПУСТИМО**.

```text
DUPLICATE_DETECTED_BEFORE_DISK_WRITE:                          YES
POST_SIDE_EFFECT_IN_MEMORY_STATE_CAN_PRECEDE_DISK_VALIDATION:  YES
GENERATED_COLLISION_MUST_BE_PREVENTED_BEFORE_CANDIDATE:        YES
PERSISTENCE_DUPLICATE_VALIDATION:                              DEFENSE_IN_DEPTH
COLLISION_SKIP_REQUIRED:                                       YES
```
Валидаторы `state_store` и `persistence.rs` выполняют исключительно роль эшелонированной защиты (defense-in-depth).

### 9.3. Обоснование неизменяемости зарезервированного набора
Сгенерированные идентификаторы не требуется динамически добавлять в `reserved_ids`, поскольку:
* Экземпляр `WindowsIdSequence` разделяется между обоими методами `next_timer_id` и `next_outbox_id`;
* Локальная 128-битная последовательность монотонно возрастает и не может повториться на протяжении $2^{128}$ шагов;
* Набор `reserved_ids` предназначен исключительно для изоляции от идентификаторов, переживших перезапуск службы от предыдущих запусков процесса.

## 10. Пространства имен и семантика перезапуска (Namespaces & Restart Semantics)

### 10.1. Пространства имен идентификаторов
```text
TIMER_NAMESPACE:                                  TimerId
OUTBOX_NAMESPACE:                                 OutboxEntryId
CROSS_NAMESPACE_UNIQUENESS_SEMANTICALLY_REQUIRED: NO
SHARED_PRODUCTION_SEQUENCE:                       YES
```
* Производственный адаптер разделяет единую 128-битную последовательность между генерацией идентификаторов таймеров и очереди исходящих сообщений.
* До момента исчерпания полного периода локальной последовательности в $2^{128}$ шагов генерируемые ею значения гарантированно не повторяются, и, следовательно, формируемые данным процессом значения `TimerId` и `OutboxEntryId` не имеют одинаковых байтов.
* После полного исчерпания периода последовательности гарантия неповторяемости не предоставляется.
* Доменный код **КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН** полагаться на неравенство байтов `TimerId` и `OutboxEntryId` как на смысловое правило предметной области (типы остаются изолированными).
* Проверка дубликатов на уровне персистентности остается раздельной по коллекциям (`active_actions` и `telegram_outbox`).

### 10.2. Семантика перезапуска службы
```text
RESTART_COUNTER_PERSISTENCE_REQUIRED: NO
RESTART_CONTINUITY_REQUIRED:          NO
PROBABILISTIC_RESTART_UNIQUENESS:     YES
ABSOLUTE_GLOBAL_LIFETIME_UNIQUENESS:  NO
```
* Каждый перезапуск процесса службы извлекает свежий 128-битный случайный сид через `BCryptGenRandom`.
* Ведение постоянного счетчика в файле или базе данных на диске не требуется и прямо запрещено.
* Исторические идентификаторы, завершенные и удаленные из авторитетного файла `state.json`, не хранятся в постоянных глобальных реестрах.

## 11. Модель безопасности (Security & Predictability)

```text
UNPREDICTABILITY_SECURITY_REQUIRED: NO
UNIQUENESS_REQUIRED:                YES
OPAQUE_REPRESENTATION_REQUIRED:     YES
```
1. Идентификаторы `TimerId` и `OutboxEntryId` **НЕ ЯВЛЯЮТСЯ** секретами авторизации или токенами аутентификации.
2. Идентификаторы **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** использовать в качестве:
   * Паролей или родительских PIN-кодов;
   * Токенов доступа Telegram Bot API;
   * Авторизационных сессионных bearer-токенов IPC;
   * Криптографических ключей.
3. Случайный выбор сида при старте процесса служит исключительно целям вероятностного разделения пространств идентификаторов между перезапусками, а не обеспечению криптографической тайны сущностей.

## 12. Поведение на отличных от Windows платформах (Non-Windows Behavior)

1. Кодовая база репозитория на платформе `!cfg(windows)` (например, при сборке под Linux/macOS) **ОБЯЗАНА** успешно компилироваться.
2. При попытке вызова производственного конструктора на не-Windows платформах конструктор **ОБЯЗАН** возвращать явную типизированную ошибку:
   `WindowsIdGeneratorError::UnsupportedPlatform` (или ее эквивалент в домене ошибок службы).
3. Создание фиктивных заглушек, выдающих псевдослучайные последовательности в производственном режиме, строго запрещено.

## 16. Граница физической интеграции Windows (Windows Integration Boundary)

Проверка **`IDS-03`** является единственной строкой матрицы, требующей физического исполнения против реального API CNG на хосте Windows.
* Тест является абсолютно безопасным, пассивным и немодифицирующим состояние операционной системы.
* Прохождение модульных тестов без участия реального API CNG не признается доказательством выполнения `IDS-03`.
* Физическое исполнение `IDS-03` относится к последующему этапу реализации (`PRODUCTION-ID-SOURCE IMPLEMENTATION`).

## 18. Категорические архитектурные исключения (Explicit Non-Goals)

Настоящий контракт категорически и безальтернативно отвергает следующие решения:
1. Вызов `BCryptGenRandom` при каждом запросе идентификатора из `IdSource::next_*`;
2. Использование функции `UuidCreate` в качестве канонического генератора V1;
3. Введение нормативных требований формата UUID v4 (биты варианта и версии);
4. Создание файла дискового счетчика или базы данных последовательностей между перезапусками;
5. Генерация идентификаторов на базе одного лишь системного времени (timestamp-only);
6. Использование PID, thread ID или MAC-адресов для формирования идентификаторов;
7. Использование machine GUID;
8. Использование псевдослучайных генераторов без криптографической стойкости при сбое CNG;
9. Использование паник, `unwrap` или `expect` при обработке системных кодов возврата CNG;
10. Изменение сигнатур методов существующего трейта `IdSource` в `runtime.rs`;
11. Введение глобального статического изменяемого состояния (global mutable static);
12. Раздельные локальные счетчики для таймеров и очереди Telegram;
13. Внедрение фиктивного `FakeIdSource` в производственный состав исполняемого файла службы.
