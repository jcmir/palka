# Контракт жизненного цикла Windows Service (Windows Service Lifecycle Contract)

Документ определяет нормативные требования к интеграции службы `palka-service` с Windows Service Control Manager (SCM), конфигурации установки, учетной записи, автоматическому запуску, политикам восстановления при сбоях, обработке управляющих сигналов, модели конечного автомата состояний и разграничению прав доступа (anti-tamper).

---

## 1. Архитектурное разделение ответственности

В рамках базового инварианта архитектуры PALKA:
* `CORE DECIDES` — принимает доменные решения.
* `SERVICE ENFORCES` — обеспечивает непрерывное принудительное исполнение политик.
* `PLATFORM EXECUTES` — выполняет системные вызовы операционной системы.
* `TRAY DISPLAYS` — отображает пользовательский интерфейс.
* `TELEGRAM REQUESTS` — принимает удаленные запросы родителя.

Ответственность за жизненный цикл Windows Service разделяется между компонентами:

1. **`palka-service` (`SERVICE`)**:
   * Является процессом службы Windows Service (`SERVICE_WIN32_OWN_PROCESS`);
   * Владеет жизненным циклом и состоянием службы;
   * Регистрирует точку входа службы и обработчик управляющих сигналов (Service Control Handler);
   * Управляет переходами статусов SCM (`START_PENDING`, `RUNNING`, `STOP_PENDING`, `STOPPED`);
   * Инициирует авторитетный runtime планировщика и принудительного исполнения после перехода в `SERVICE_RUNNING`;
   * Обеспечивает корректное (graceful) завершение runtime при получении авторизованного сигнала `SERVICE_CONTROL_STOP`.

2. **`palka-windows-platform` (`PLATFORM`)**:
   * Содержит низкоуровневые вызовы Win32 SCM API (OpenSCManagerW, CreateServiceW, ChangeServiceConfigW, ChangeServiceConfig2W, QueryServiceStatusEx, QueryServiceConfigW и др.);
   * Предоставляет типизированные абстракции для установки, параметризации, запроса конфигурации и удаления службы;
   * Предоставляет типизированную конфигурацию политик восстановления (Service Failure Actions);
   * Реализует адаптер диспетчеризации службы и обновления статуса через Win32 API.

Введение дополнительных runtime-компонентов или фоновых служб-прокладок категорически запрещено.

---

## 2. Идентификация и тип службы (Service Identity & Type)

Зафиксированы неизменяемые (immutable для V1) идентификаторы службы:

* **`SERVICE_NAME`**: `PalkaService`
* **`SERVICE_DISPLAY_NAME`**: `PALKA Service`
* **`SERVICE_DESCRIPTION`**: `PALKA parental control enforcement service`

Использование локализованных или альтернативных имен службы запрещено.

### Тип службы (Service Type)
* Нормативное значение: **`SERVICE_WIN32_OWN_PROCESS`** (служба выполняется в собственном изолированном процессе `palka-service.exe`).
* Запрещены:
  * `SERVICE_INTERACTIVE_PROCESS` (интерактивные службы запрещены требованиями безопасности Windows);
  * Разделяемые процессы (Shared Process / `svchost.exe`);
  * Драйверы режима ядра (Kernel Driver / File System Driver);
  * Пользовательские службы сеанса (Per-user Services).

---

## 3. Учетная запись службы (Service Account)

* Нормативная учетная запись: **`LocalSystem`** (логический субъект безопасности: `NT AUTHORITY\SYSTEM`).
* Запрещено использование:
  * `LocalService`;
  * `NetworkService`;
  * Учетной записи ребенка (`Child`);
  * Учетной записи родителя (`Parent`);
  * Пользовательских сервисных учетных записей с сохраняемым паролем.

Служба запускается без сохранения паролей в SCM или диспетчере учетных данных (LSA Secrets). Права `LocalSystem` необходимы для автономного применения сетевой фильтрации WFP, принудительного завершения процессов, выключения ПК и защиты хранилища `%ProgramData%\Palka`.

---

## 4. Режим запуска и зависимости (Start Mode & Dependencies)

### Режим запуска (Start Type)
* Нормативное значение: **`SERVICE_AUTO_START`** (автоматический запуск при старте операционной системы).
* Отложенный автоматический запуск (**Delayed Auto-Start**): **`DISABLED`** (`FALSE`).

> [!IMPORTANT]
> Принудительное исполнение родительского контроля должно активироваться на максимально ранней стадии загрузки Windows и быть активным до входа любого пользователя в систему.

### Контроль ошибок запуска (Error Control)
* Нормативное значение: **`SERVICE_ERROR_NORMAL`**.

### Зависимости службы (Dependencies)
* Нормативное значение: **`NONE`** (пустой список зависимостей).
* Запрещены зависимости от:
  * Интерактивного сеанса пользователя или процесса `tray`;
  * Доступности сети Интернет или Telegram API;
  * Конкретных пользовательских профилей или сессий.

Отсутствие доступа к сети Интернет не должно блокировать запуск, инициализацию или авторитетное исполнение службы.

---

## 5. Контракт бинарного пути (Binary Path Contract)

Путь запуска в SCM (`lpBinaryPathName`) должен указывать на канонический исполняемый файл `palka-service.exe`:

1. **Только абсолютный путь**: Относительные пути, пустые строки и спецсимволы категорически запрещены.
2. **Нулевой байт (NUL)**: Наличие встроенных символов `\0` запрещено (fail-closed валидация).
3. **Экранирование пробелов**: Если абсолютный путь содержит пробелы, он должен быть корректно заключен в двойные кавычки в соответствии с правилами Win32 SCM (во избежание уязвимостей Unquoted Service Path).
4. **Запрет оболочек**: Запрещен запуск через `cmd.exe`, `powershell.exe`, `.bat`, `.cmd` или скриптовые обертки.
5. **Параметры командной строки**: Процесс V1 не требует передачи произвольных аргументов командной строки при стандартном запуске через SCM.

---

## 6. Идемпотентный контракт установки (SCM Provisioning Contract)

Установка и изменение параметров службы являются привилегированными операциями администрирования (выполняются установщиком или администратором с повышенными привилегиями `Elevated Administrator` или `SYSTEM`).

1. **Разделение задач**: Runtime-процесс службы не должен при каждом штатном запуске самопроизвольно переустанавливать себя в SCM, менять бинарный путь, учетную запись или DACL службы.
2. **Идемпотентность провижининга**:
   * Если служба отсутствует в SCM — создается новая служба с канонической конфигурацией;
   * Если служба уже существует — проверяется соответствие текущей конфигурации канонической, и при необходимости параметры приводятся к нормативным;
   * Возврат `ERROR_SERVICE_EXISTS` от `CreateServiceW` не считается автоматическим успехом без сверки параметров конфигурации.
3. **Обязательный Query-Back**: После завершения операции создания/обновления конфигурации выполняется обратный запрос (`QueryServiceConfigW` / `QueryServiceConfig2W`) с подтверждением фактического применения всех канонических параметров.

## 7. Политика восстановления при сбоях (Service Recovery Policy)

Для защиты от аварийных сбоев и саботажа путем краша процесса служба конфигурируется с жестко заданной нормативной политикой восстановления Windows SCM:

* **Период сброса счетчика сбоев (`dwResetPeriod`)**: **`86400` секунд** (24 часа).
* **Перезапуск при сбоях (`SC_ACTION_RESTART`)**:
  * **Сбой №1 (First failure)**: Перезапуск службы через **`5000` мс** (5 секунд).
  * **Сбой №2 (Second failure)**: Перезапуск службы через **`15000` мс** (15 секунд).
  * **Сбой №3 и последующие (Subsequent failures)**: Перезапуск службы через **`60000` мс** (60 секунд).
* **Запрещенные действия восстановления**:
  * **`SC_ACTION_REBOOT`** — КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО (служба никогда не должна перезагружать операционную систему в качестве recovery-действия);
  * **`SC_ACTION_RUN_COMMAND`** — КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО (служба не должна запускать внешние исполняемые файлы или скрипты при сбое).

### Флаг действий при неаварийном завершении (`fFailureActionsOnNonCrashFailures`)
* Нормативное значение: **`FALSE`** (действия восстановления применяются исключительно при аварийном завершении/падении процесса).
* Контролируемая штатная остановка администратором, завершающаяся статусом `SERVICE_STOPPED`, не должна приводить к автоматическому перезапуску службы SCM.

---

## 8. Обработка управляющих сигналов (SCM Control Contract)

### Поддерживаемые сигналы управления
* **`SERVICE_CONTROL_STOP`**: Поддерживается.
* **`SERVICE_CONTROL_SHUTDOWN`**: Поддерживается (корректная реакция на завершение работы операционной системы Windows).

### Запрещенные и неподдерживаемые сигналы управления
* **`SERVICE_CONTROL_PAUSE`**: **НЕ ПОДДЕРЖИВАЕТСЯ** (служба не объявляет возможность паузы `SERVICE_ACCEPT_PAUSE_CONTINUE`).
* **`SERVICE_CONTROL_CONTINUE`**: **НЕ ПОДДЕРЖИВАЕТСЯ**.
* Пользовательские (User-defined) SCM control codes в V1 не используются.

### Принятие управляющих сигналов (`dwControlsAccepted`)
* В состоянии `SERVICE_RUNNING`: устанавливается флаг `SERVICE_ACCEPT_STOP` (и при необходимости `SERVICE_ACCEPT_SHUTDOWN`).
* Флаги `SERVICE_ACCEPT_PAUSE_CONTINUE` категорически исключаются.

Право на отправку сигнала `SERVICE_CONTROL_STOP` регулируется дескриптором безопасности службы Windows SCM. Родитель (Administrator) имеет право штатно остановить службу. Ребенок (Standard User) не обладает правами на остановку службы.

---

## 9. Автомат состояний службы (SCM State Machine)

Служба реализует строгий конечный автомат жизненного цикла SCM:

```
[SCM Process Launch]
        │
        ▼
 SERVICE_START_PENDING  ──(ошибка bootstrap)──►  SERVICE_STOPPED (ExitCode != 0)
        │
 (успешный bootstrap)
        │
        ▼
   SERVICE_RUNNING
        │
 (получен авторизованный SERVICE_CONTROL_STOP)
        │
        ▼
  SERVICE_STOP_PENDING
        │
 (graceful runtime teardown завершен)
        │
        ▼
   SERVICE_STOPPED (ExitCode = 0)
```

1. **`SERVICE_START_PENDING`**:
   * Устанавливается немедленно после входа в `ServiceMain`.
   * Значение `dwWaitHint` устанавливается достаточным для инициализации (например, 10 000 мс).
   * При длительной инициализации значение `dwCheckPoint` монотонно инкрементируется.
   * Выполняется базовый bootstrap хранилища `%ProgramData%\Palka`, валидация канонических файлов и инициализация подсистем.
   * При критическом сбое bootstrap служба сообщает `SERVICE_STOPPED` с ненулевым кодом завершения.
2. **`SERVICE_RUNNING`**:
   * Устанавливается только после успешного завершения обязательного bootstrap.
   * Служба сообщает `dwControlsAccepted = SERVICE_ACCEPT_STOP | SERVICE_ACCEPT_SHUTDOWN`.
   * Запускается авторитетный цикл планировщика и принудительного исполнения.
3. **`SERVICE_STOP_PENDING`**:
   * Устанавливается при получении авторизованного сигнала `SERVICE_CONTROL_STOP`.
   * Запрещается прием новых IPC-запросов и задач.
   * Передается сигнал завершения авторитетному runtime.
   * Значение `dwCheckPoint` инкрементируется до завершения фоновых потоков и сохранения состояния на диск.
4. **`SERVICE_STOPPED`**:
   * При штатной остановке администратором: Win32 Exit Code = `ERROR_SUCCESS` (0).
   * При фатальном сбое: код ошибки отражает природу отказа; ошибка не маскируется под `ERROR_SUCCESS`.

## 10. Политика безопасности и разграничения доступа (Service DACL & Anti-Tamper)

1. **Штатный дескриптор безопасности SCM**:
   * V1 опирается на стандартную модель безопасности Windows Service Control Manager, запрещающую стандартным пользователям управление службами;
   * Запрещено создание кастомных ослабленных DACL, предоставляющих права группам `Everyone`, `BUILTIN\Users` или `Authenticated Users`.
2. **Ограничение прав ребенка (`Child Standard User`)**:
   Пользователь с правами стандартного пользователя Windows **КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН (SHALL NOT)** иметь следующие эффективные права на объект службы:
   * `SERVICE_STOP` (остановка службы);
   * `SERVICE_PAUSE_CONTINUE` (приостановка службы);
   * `SERVICE_CHANGE_CONFIG` (изменение параметров запуска или бинарного пути);
   * `DELETE` (удаление службы из реестра SCM);
   * `WRITE_DAC` (модификация списка контроля доступа службы);
   * `WRITE_OWNER` (смена владельца службы).
   * *Примечание*: Права на опрос статуса (`SERVICE_QUERY_STATUS`, `SERVICE_QUERY_CONFIG`, `SERVICE_INTERROGATE`) не нарушают модель угроз и являются допустимыми.
3. **Права администратора (`Parent Administrator`)**:
   * Сохраняет полный административный контроль над службой через стандартные системные инструменты (`sc.exe`, `Stop-Service`, `services.msc`).
4. **Права службы (`NT AUTHORITY\SYSTEM`)**:
   * Обладает полными правами на управление своим объектом службы и взаимодействие с SCM.

---

## 11. Автономность от интерактивного сеанса и Tray

* **Независимость от Logon**: Служба запускается и выполняет принудительное исполнение до входа пользователя в систему, при заблокированном экране и после выхода пользователя из сеанса (`Logoff`).
* **Изоляция от `tray`**:
  * Процесс `palka-tray.exe` не является службой Windows;
  * `palka-tray.exe` не управляет планировщиком и не владеет авторитетным состоянием;
  * Завершение, зависание или крах `palka-tray.exe` никоим образом не влияют на выполнение `palka-service.exe`.

---

## 12. Non-Windows платформы

На платформах, отличных от Windows (`#[cfg(not(windows))]`), вызов публичного API управления Windows Service / SCM завершается контролируемой ошибкой `UnsupportedPlatform` (fail-closed). Создание имитаций SCM на других ОС в качестве границы безопасности запрещено.

---

## 13. Матрица верификации (Verification Traceability Matrix)

Для подтверждения соответствия реализации настоящему контракту определены обязательные нормативные идентификаторы верификации:

| Идентификатор | Описание верифицируемого требования | Уровень свидетельства |
|---|---|---|
| **SCM-01** | Канонические имена (`SERVICE_NAME`, `SERVICE_DISPLAY_NAME`, `SERVICE_DESCRIPTION`), тип `SERVICE_WIN32_OWN_PROCESS`, учетная запись `LocalSystem`. | V1 / V2 (Contract/Unit) |
| **SCM-02** | Режим запуска `SERVICE_AUTO_START`, отложенный автозапуск отключен (`DelayedAutostart = false`). | V1 / V2 / V3 |
| **SCM-03** | Точные параметры восстановления: период сброса 86400 с, задержки рестарта 5 с / 15 с / 60 с. | V1 / V2 / V3 |
| **SCM-04** | Отсутствие действия перезагрузки ОС (`SC_ACTION_REBOOT`) в конфигурации восстановления. | V1 / V2 / V3 |
| **SCM-05** | Отсутствие действия запуска внешних команд (`SC_ACTION_RUN_COMMAND`) в конфигурации восстановления. | V1 / V2 / V3 |
| **SCM-06** | Бинарный путь абсолютный, не пустой, не содержит NUL, корректно экранирован кавычками при наличии пробелов. | V1 / V2 / V3 |
| **SCM-07** | Идемпотентность установки и обязательная сверка параметров через обратный запрос (Query-Back). | V2 / V3 |
| **SCM-08** | Корректная смена статусов при запуске: `START_PENDING` -> `RUNNING` (с инкрементом чекпоинта). | V2 / V3 |
| **SCM-09** | Корректная смена статусов при штатной остановке администратором: `RUNNING` -> `STOP_PENDING` -> `STOPPED` (ExitCode = 0). | V2 / V3 |
| **SCM-10** | Запросы паузы и продолжения (`PAUSE` / `CONTINUE`) отклоняются / не поддерживаются (`ControlsAccepted` не содержит `ACCEPT_PAUSE_CONTINUE`). | V1 / V2 / V3 |
| **SCM-11** | Автономная работа службы без интерактивного входа пользователя и без запущенного процесса `tray`. | V3 / V4 |
| **SCM-12** | Стандартный пользователь (`Child Standard User`) получает `Access Denied` при попытке вызова `SERVICE_CONTROL_STOP`. | V4 (Security Acceptance) |
| **SCM-13** | Стандартный пользователь (`Child Standard User`) получает `Access Denied` при попытке вызова `SERVICE_CONTROL_PAUSE`. | V4 (Security Acceptance) |
| **SCM-14** | Стандартный пользователь (`Child Standard User`) получает `Access Denied` при попытке вызова `CHANGE_CONFIG`. | V4 (Security Acceptance) |
| **SCM-15** | Стандартный пользователь (`Child Standard User`) получает `Access Denied` при попытке вызова `DELETE`. | V4 (Security Acceptance) |
| **SCM-16** | Администратор (`Parent Administrator`) сохраняет полные права управления службой. | V3 / V4 |
| **SCM-17** | Аварийный крах процесса службы приводит к автоматическому перезапуску SCM в соответствии с recovery policy. | V4 (E2E Recovery) |
| **SCM-18** | Многократные аварийные завершения службы последовательно используют задержки 5с -> 15с -> 60с. | V4 (E2E Recovery) |
| **SCM-19** | Штатная контролируемая остановка службы администратором не активирует перезапуск по recovery policy. | V3 / V4 |
| **SCM-20** | Вызов API на платформах, отличных от Windows, возвращает типизированную ошибку `UnsupportedPlatform` (Fail-Closed). | V1 / V2 |

### Уровни доказательности (Evidence Levels)
* **V1/V2**: Проверка чистого парсинга структур, валидации параметров путей, строк и типов аргументов в изолированных юнит-тестах.
* **V3**: Обязательное интеграционное тестирование взаимодействия с реальным Windows SCM API на платформе Windows в CI / staging.
* **V4**: Обязательное подтверждение на этапе приемочного тестирования безопасности (Security Acceptance) эффективных прав в контексте токена реального стандартного пользователя Windows и физического перезапуска после падения процесса.
