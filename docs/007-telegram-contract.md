# Контракт интеграции с Telegram (Telegram Contract)

Документ определяет спецификацию удаленного управления и взаимодействия через мессенджер Telegram. Все команды и события соответствуют [Доменному контракту](./002-domain-contract.md).

## 1. Авторизационный барьер и безопасность

1. **Белый список идентификаторов (Whitelist Authorization)**:
   * Доступ к управлению ДОЛЖЕН (SHALL) быть строго ограничен списком разрешенных `ChatId` и `UserId`, зафиксированных в защищенной конфигурации службы.
   * Сообщения от неавторизованных идентификаторов немедленно и безусловно отбрасываются.
2. **Абсолютный запрет произвольного исполнения (Strict Domain Scope)**:
   * Telegram-адаптер ДОЛЖЕН (SHALL) поддерживать только строго определенный замкнутый перечень доменных команд.
   * **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО**:
     * выполнение произвольных системных команд или утилит командной строки;
     * запуск скриптов PowerShell, CMD или Bash;
     * чтение, модификация, исполнение или передача произвольных файлов;
     * управление произвольными процессами операционной системы.

## 2. Поддерживаемые доменные команды и парсинг длительности

| Команда Telegram | Доменная `Command` | Описание |
| :--- | :--- | :--- |
| `/status` | `QueryStatus` | Запрос текущего снимка состояния системы ([`StatusSnapshot`](./002-domain-contract.md)) |
| `/block <длительность>` | `ScheduleInternetBlock { duration_minutes }` | Планирование блокировки интернета |
| `/block_now` | `ImmediateInternetBlock` | Немедленная принудительная блокировка доступа в Интернет |
| `/unblock` | `RestoreInternet` | Немедленное снятие блокировки доступа в Интернет |
| `/cancel_block` | `CancelInternetBlockTimer` | Отмена активного таймера блокировки интернета |
| `/shutdown <длительность>` | `ScheduleShutdown { duration_minutes }` | Планирование выключения компьютера |
| `/cancel_shutdown` | `CancelShutdownTimer` | Отмена активного таймера выключения (до дедлайна) |
| `/msg <текст>` | `SendParentMessage { text }` | Отправка текстового сообщения ребенку в трей |

### 2.1. Формат ввода длительности (Duration Syntax)
* Telegram-адаптер поддерживает синтаксис относительного времени, включающий:
  * `30m` (минуты);
  * `2h` (часы);
  * `1h30m` (комбинация часов и минут).
* Адаптер нормализует эти значения в доменную длительность (`duration_minutes`).
* Некорректные, нулевые или выходящие за допустимые пределы значения длительности отклоняются с возвратом сообщения об ошибке и **НЕ ДОЛЖНЫ (MUST NOT)** изменять текущие активные таймеры.

## 3. Проактивный мониторинг здоровья и диагностический пульс (Health Reporting)

1. **Оповещения жизненного цикла и сбоев**:
   * Служба автоматически отправляет уведомления в авторизованный Telegram-чат при наступлении событий:
     * `ServiceReady` — служба завершила инициализацию после старта ОС (включая результат восстановления сетевой политики);
     * `ServiceHealthChanged` — переход в `HealthStatus::Degraded` или `Critical` с указанием причины сбоя;
     * `ServiceHealthChanged` — восстановление состояния в `HealthStatus::Healthy`;
     * `MissedDeadlineOccurred` — пропуск выключения компьютера при старте системы после просроченного дедлайна;
     * `WarningThresholdReached` — наступление порога предупреждения (60m, 30m, 20m, 10m, 3m).
2. **Диагностический пульс (Periodic Heartbeat)**:
   * Служба поддерживает периодическую отправку краткого информационного сообщения (Heartbeat), содержащего:
     * статус здоровья (`ServiceHealth`);
     * целевую и наблюдаемую политику сети (`DesiredInternetState` и `InternetState`);
     * остаток времени по активному таймеру интернета (если есть);
     * остаток времени по активному таймеру выключения (если есть);
     * время непрерывной работы (`uptime`).
   * Частота отправки настраивается в конфигурации.

## 4. Семантика доставки сообщений (Delivery Semantics)

1. **Гарантии доставки**:
   * Система не заявляет гарантий «ровно один раз» (exactly-once) через внешнюю сеть.
   * Исходящее сообщение атомарно сохраняется в персистентную очередь со статусом `AcceptedByService` до попытки отправки.
   * При временных сетевых сбоях выполняются повторные попытки с экспоненциальной задержкой (bounded backoff).
   * Сообщение помечается статусом `AcceptedByTelegram` только после получения явного подтверждения (`ack`) от HTTP API Telegram.
   * При аварийном перезапуске возможна повторная отправка (at-least-once), но молчаливая потеря недоставленного сообщения исключена.
