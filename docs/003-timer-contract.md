# Контракт подсистемы таймеров (Timer Contract)

Документ определяет нормативные правила расчета, отслеживания, восстановления и исполнения запланированных действий (`ScheduledAction`) и формирования предупреждающих событий (`WarningEvent`). Все типы соответствуют [Доменному контракту](./002-domain-contract.md).

## 1. Пороги предупреждений (Warning Thresholds)

1. Для любого запланированного действия (`ActionKind::BlockInternet` или `ActionKind::ShutdownComputer`) система ДОЛЖНА (SHALL) поддерживать ровно пять фиксированных порогов предупреждения:
   * `WarningThreshold::M60` (60 минут / 3600 секунд до дедлайна);
   * `WarningThreshold::M30` (30 минут / 1800 секунд до дедлайна);
   * `WarningThreshold::M20` (20 минут / 1200 секунд до дедлайна);
   * `WarningThreshold::M10` (10 минут / 600 секунд до дедлайна);
   * `WarningThreshold::M3`  (3 минуты / 180 секунд до дедлайна).
2. Предупреждение для конкретного порога в рамках одного `TimerId` формируется **не более одного раза**.

## 2. Детерминированное пересечение порогов (Threshold Crossing Semantics)

Для исключения зависимости от миллисекундной точности пробуждения планировщика пересечение порога вычисляется по дискретной схеме изменения остатка времени:

1. **Условие срабатывания порога**:
   Порог `threshold` считается наступившим (`due`) в момент дискретного шага планировщика, если одновременно выполнены три условия:
   ```text
   previous_remaining > threshold
   AND
   current_remaining <= threshold
   AND
   threshold NOT IN emitted_thresholds
   ```
   *Пример*: Если на предыдущем тике остаток был 10 минут 05 секунд, а на текущем тике составляет 9 минут 58 секунд, порог `M10` срабатывает ровно один раз.

2. **Правила инициализации при создании таймера**:
   При создании нового таймера с длительностью `duration`:
   * если `duration > threshold` — порог остается в статусе ожидаемого (будущего);
   * если `duration == threshold` — порог наступает немедленно после успешной персистентной фиксации таймера;
   * если `duration < threshold` — порог автоматически заносится в `emitted_thresholds` как пройденный без генерации уведомления.

3. **Правила восстановления при перезапуске службы (Recovery Equality Rule)**:
   При возобновлении работы службы с активным таймером, дедлайн которого находится в будущем (`current_remaining > 0`):
   * все пороги, удовлетворяющие условию `threshold >= current_remaining`, считаются пройденными во время недоступности и заносятся в `emitted_thresholds` без ретроактивной генерации;
   * только пороги, удовлетворяющие условию `threshold < current_remaining`, сохраняют право на последующую генерацию предупреждений.

4. **Приоритет дедлайна перед предупреждениями**:
   Если `current_remaining <= 0`, система немедленно исполняет логику дедлайна. Устаревшие промежуточные предупреждения не генерируются.

## 3. Жизненный цикл и долговечность исполнения

### 3.1. Создание, замещение и отмена таймеров
* **Создание**: Вычисляется дедлайн `Deadline = CurrentUtcTime + duration`. Запись `ScheduledAction` переводится в `ActionExecutionState::Pending` и атомарно сохраняется на диск.
* **Замещение**: Для каждого `ActionKind` существует не более одного активного таймера. Новая команда того же типа аннулирует старый таймер (`Event::TimerCancelled`) и создает новый `ScheduledAction`.
* **Отмена (Граница авторизации отмены выключения)**:
  * Команда `CancelShutdownTimer` правомочна **ИСКЛЮЧИТЕЛЬНО ДО НАСТУПЛЕНИЯ ДЕДЛАЙНА** (`current_remaining > 0`).
  * При наступлении или после наступления дедлайна (`current_remaining <= 0`) действие переходит в фазу исполнения и **НЕ МОЖЕТ БЫТЬ ОТМЕНЕНО** через `CancelShutdownTimer`.

### 3.2. Долговечное исполнение истекших таймеров (Execution Durability)
Истекший таймер **КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН (MUST NOT)** удаляться из состояния до тех пор, пока служба не завершит операцию принудительного исполнения:

#### А. Блокировка Интернета (`BlockInternet` и `ImmediateInternetBlock`):
`ImmediateInternetBlock` и истечение таймера `BlockInternet` используют единый отказоустойчивый путь исполнения:
1. Целевая политика службы переводится в `DesiredInternetState::Blocked`.
2. Запись `ScheduledAction` переводится в состояние `ActionExecutionState::Executing` и атомарно сохраняется на диск.
3. Служба вызывает метод `InternetGate::block_internet` через платформенный слой.
4. При успешном исполнении:
   * наблюдаемое состояние обновляется: `observed_internet_state = InternetState::Blocked`;
   * действие переводится в статус `Completed` и удаляется из активного набора;
   * генерируется `Event::InternetPolicyChanged`.
5. При ошибке `InternetGate`:
   * действие переходит в `ActionExecutionState::Failed { reason }` и сохраняется на диск;
   * целевая политика `desired` остается `Blocked`, а наблюдаемое состояние — `Unrestricted` или `Unknown`;
   * статус службы переводится в `ServiceHealth::Degraded` или `Critical`;
   * родителю в Telegram отправляется уведомление об ошибке;
   * служба производит повторные попытки применения с ограниченной экспоненциальной задержкой (bounded backoff: 5с, 15с, 30с; бесконечные плотные циклы ЗАПРЕЩЕНЫ).

#### Б. Выключение компьютера (`ShutdownComputer`):
1. В момент дедлайна `core` фиксирует наступление дедлайна (`TimerExpired`).
2. Служба вызывает метод `PowerController::initiate_shutdown()` через платформенный слой.
3. После принятия запроса ОС Windows статус переводится в `ShutdownState::InProgress`.

### 3.3. Дифференциация просроченных дедлайнов при старте службы (Missed Deadlines)
1. **Для `BlockInternet`**:
   * Блокировка применяется немедленно при старте службы через `InternetGate`.
2. **Для `ShutdownComputer` (Защита от цикла перезагрузок)**:
   * Система **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНА (MUST NOT)** производить немедленное выключение загруженного компьютера.
   * Действие переводится в `ActionExecutionState::Missed`, старый таймер аннулируется, статус питания устанавливается в `ShutdownState::Idle`.
   * Родителю в Telegram отправляется уведомление `MissedDeadlineOccurred`.

## 4. Семантика времени: Системные часы vs Монотонный таймер

1. **Непрерывная работа службы (Runtime Operation)**:
   * Для каждого относительного таймера фиксируется абсолютный UTC `Deadline` (для восстановления после перезапуска).
   * Внутри работающего процесса службы обратный отсчет, интервалы и тики планировщика управляются **монотонным таймером ОС (Monotonic Clock / Instant)**.
   * **Нормативные гарантии**:
     * перевод системных часов Windows назад во время работы службы **НЕ МОЖЕТ** продлить длительность таймера;
     * перевод системных часов Windows вперед во время работы службы **НЕ МОЖЕТ** преждевременно завершить таймер;
     * перевод часов не может вызвать дублирование предупреждений.
2. **Перезапуск службы (Restart Recovery)**:
   * При старте службы монотонный таймер инициализируется заново, а остаток времени вычисляется по сохраненному абсолютному UTC `Deadline`.
   * Если дедлайн оказался в прошлом, применяются правила просроченных дедлайнов (Missed Deadlines).
