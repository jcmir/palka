# Контракт шлюза управления Интернетом (InternetGate Contract)

Документ определяет абстрактный контракт компонента `InternetGate`, отвечающего за селективное принудительное ограничение доступа к сети Интернет для сконфигурированного пользователя Windows.

## 1. Абстрактный интерфейс `InternetGate`

`InternetGate` является абстрактным интерфейсом подсистемы `windows-platform`, инкапсулирующим детали реализации сетевой фильтрации на уровне ОС Windows. Канонический трейт `InternetGate` определен в `crates/service/src/runtime.rs` и реэкспортирован через `crates/service/src/lib.rs` (`palka_service::InternetGate`).

```rust
pub trait InternetGate: Send + Sync {
    fn current_state(&self, child_sid: &str) -> Result<InternetState, PlatformError>;
    fn block_internet(&self, child_sid: &str) -> Result<(), PlatformError>;
    fn unblock_internet(&self, child_sid: &str) -> Result<(), PlatformError>;
}
```

## 2. Нормативные требования к изоляции и селективности

1. **Таргетирование по SID (User SID Targeting)**:
   * Блокировка ДОЛЖНА (SHALL) применяться строго к процессам и сетевым пакетам, ассоциированным с SID (`child_sid`) сконфигурированного пользователя-ребенка.
2. **Изоляция привилегированной службы (Privileged Service Exemption)**:
   * Блокировка сети НЕ ДОЛЖНА (SHALL NOT) распространяться на трафик системной службы `service` (работающей под `NT AUTHORITY\SYSTEM`) и локального администратора.
   * Связность службы со службами Telegram Bot API, DNS и локальной сетью ДОЛЖНА (SHALL) полностью сохраняться при любом состоянии `DesiredInternetState` и `InternetState`.
3. **Сохранение локального IPC**:
   * Сетевая блокировка не должна нарушать локальный обмен через Named Pipes между `tray` и `service`.

## 3. Требования к принудительному исполнению и разрыву соединений (Enforcement & Connection Teardown)

1. **Политика vs Физическое принуждение**:
   * Значение `DesiredInternetState::Blocked` выражает авторитарную целевую политику службы (намерение привести систему к заблокированному состоянию) и само по себе не является доказательством физической блокировки трафика.
   * Фактическое принудительное исполнение осуществляется вызовом `InternetGate::block_internet(child_sid)` и подтверждается через `InternetGate::current_state(child_sid)`.
2. **Критерии успешного принудительного исполнения (Blocked Policy Satisfaction)**:
   Для признания политики `Blocked` успешно исполненной на платформе:
   * открытие новых сетевых соединений (TCP SYN, UDP flows) для Child SID должно быть заблокировано;
   * добавление блокирующих фильтров на затрагиваемые слои авторизации ALE приводит к реавторизации существующих потоков при смене политики (policy-change reauthorization): первый последующий пакет, проходящий через существующий поток ALE, созданный на затрагиваемом слое, направляется на повторную авторизацию, отклоняется фильтром жесткой блокировки PALKA и приводит к разрыву потока;
   * подсистема фильтрации не гарантирует генерацию специализированных пакетов TCP RST и не делает абсолютных утверждений о пакетах или байтах, уже находившихся в очереди стека или в передаче (in flight) до наступления реавторизации;
   * обязательный интеграционный тест реавторизации и разрыва потоков существующих соединений должен быть успешно пройден.
3. **Обработка несовпадения состояний**:
   * Комбинация `DesiredInternetState::Blocked` и `InternetState::Unrestricted` (или `Unknown`) свидетельствует о незавершенном согласовании или сбое платформы. Служба обязана честно отражать это расхождение в статусе, деградировать здоровье службы, сохранять состояние повторов и уведомлять родителей.

## 4. Семантика подтверждения состояния и согласование при старте

1. **Семантика подтверждения наблюдаемого состояния**:
   * Методы `block_internet()` и `unblock_internet()` являются запросами на перевод состояния платформы.
   * Возврат `Ok(())` от метода запроса перехода **НЕ ОЗНАЧАЕТ** автоматического рапортования успеха. Служба обязана запросить подтвержденное физическое состояние через `current_state()`.
   * Наблюдаемое состояние `InternetState::Blocked` или `Unrestricted` фиксируется в системе только после успешного подтверждения от `current_state()`.
   * Если состояние не удалось подтвердить, фиксируется `InternetState::Unknown` (или сохраняется предыдущее известное), а статус службы деградирует.

2. **Двустороннее согласование политики при старте службы (Startup Reconciliation)**:
   * При инициализации служба загружает сохраненную политику `DesiredInternetState`:
     * Если `DesiredInternetState == Blocked`: служба вызывает `block_internet()` и подтверждает статус через `current_state()`.
     * Если `DesiredInternetState == Unrestricted`: служба вызывает `unblock_internet()` и подтверждает статус через `current_state()`.
   * Состояние `ServiceReady` наступает после выполнения первичной попытки согласования (даже если она завершилась ошибкой, при этом служба переходит в статус `HealthStatus::Degraded` / `Critical` и продолжает повторы).
