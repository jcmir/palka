# Контракт шлюза управления Интернетом (InternetGate Contract)

Документ определяет абстрактный контракт компонента `InternetGate`, отвечающего за селективное принудительное ограничение доступа к сети Интернет для сконфигурированного пользователя Windows.

## 1. Абстрактный интерфейс `InternetGate`

`InternetGate` является абстрактным интерфейсом подсистемы `windows-platform`, изолирующим детали реализации фильтрации сетевого трафика.

```rust
// Концептуальное представление интерфейса InternetGate
trait InternetGate: Send + Sync {
    /// Применить принудительную блокировку доступа в Интернет для указанного SID
    fn block_internet(&mut self, target_sid: &SecurityIdentifier) -> Result<(), GateError>;

    /// Восстановить (разрешить) доступ в Интернет для указанного SID
    fn unblock_internet(&mut self, target_sid: &SecurityIdentifier) -> Result<(), GateError>;

    /// Запросить текущее физическое состояние шлюза
    fn current_state(&self, target_sid: &SecurityIdentifier) -> Result<InternetState, GateError>;

    /// Проверка целостности и готовности подсистемы сетевой фильтрации
    fn check_health(&self) -> Result<(), GateError>;
}
```

## 2. Нормативные требования к изоляции и селективности

1. **Таргетирование по SID (User SID Targeting)**:
   * Блокировка ДОЛЖНА (SHALL) применяться строго к процессам и сетевым пакетам, ассоциированным с `SecurityIdentifier` (SID) сконфигурированного пользователя-ребенка.
2. **Изоляция привилегированной службы (Privileged Service Exemption)**:
   * Блокировка сети НЕ ДОЛЖНА (SHALL NOT) распространяться на трафик системной службы `service` (работающей под `NT AUTHORITY\SYSTEM` или выделенной служебной учетной записью) и локального администратора.
   * Связность службы со службами Telegram Bot API, DNS и локальной сетью ДОЛЖНА (SHALL) полностью сохраняться при любом состоянии `InternetState`.
3. **Сохранение локального IPC (Local IPC Exemption)**:
   * Сетевая блокировка не должна нарушать локальный обмен через Named Pipes между `tray` и `service`.

## 3. Требования к разрыву существующих соединений (Connection Teardown)

1. **Немедленный сброс активных сессий (Active Connection Termination)**:
   * Переход в состояние `InternetState::Blocked` ДОЛЖЕН (SHALL) не только запрещать открытие новых сетевых соединений (TCP SYN, UDP flows), но и принудительно обрывать (reset/abort) уже установленные и активные соединения целевого пользователя (включая открытые браузерные вкладки, видеостриминг, игры и фоновые соединения).
2. **Обязательство интеграционной верификации**:
   * Реализация `InternetGate` обязана доказать в интеграционных тестах факт прекращения передачи данных по уже установленному сетевому соединению (см. [Контракт тестирования](file:///c:/PALKA/docs/010-test-contract.md)).

## 4. Поведение при перезапуске и отказоустойчивость (Fail-Safe Semantics)

1. **Восстановление состояния при старте службы**:
   * Если в персистентном хранилище состояние зафиксировано как `InternetState::Blocked`, служба при старте ДОЛЖНА (SHALL) немедленно применить правила блокировки в `InternetGate` до запуска любых пользовательских процессов.
2. **Устойчивость к сбоям**:
   * При возникновении ошибки в подсистеме фильтрации компонент возвращает `GateError`, статус службы переводится в `ServiceHealth::Degraded`, а инцидент логируется и отправляется в Telegram родителям.
