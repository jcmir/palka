# Контракт производственной сетевой фильтрации Windows WFP (Windows InternetGate Contract)

## 1. Цель и границы контракта (Purpose and Scope)

Настоящий документ определяет нормативный технический контракт производственной реализации сетевого шлюза `InternetGate` для операционной системы Windows на базе подсистемы Windows Filtering Platform (WFP / BFE).

Контракт устанавливает:
1. Архитектуру взаимодействия пользовательского режима службы `palka-service` с BFE (Base Filtering Engine) через Win32 WFP API (`Fwpuclnt.dll`);
2. Модель сессии и персистентности объектов WFP (отказ от динамических сессий в пользу персистентных объектов ядра);
3. Модель идентификации субъекта сетевой блокировки на базе `SecurityIdentifier` (Child SID) и `FWPM_CONDITION_ALE_USER_ID`;
4. Точный набор слоев ALE (Application Layer Enforcement), блокирующих действий и параметров фильтров;
5. Механизм прекращения передачи данных в установленных сетевых соединениях через реавторизацию потоков ALE (policy-change reauthorization);
6. Идемпотентность и атомарность транзакций применения (`block_internet`) и снятия (`unblock_internet`) блокировки;
7. Семантику истинности наблюдаемого состояния физической фильтрации (`current_state`);
8. Модель дескрипторов безопасности (DACL) для защиты объектов фильтрации от несанкционированного изменения непривилегированным пользователем-ребенком;
9. Константы и алгоритм производственной политики повторных попыток (`InternetRetryPolicy`);
10. Типизированную таксономию ошибок уровня платформы для последующей реализации;
11. Архитектуру тестируемости с локальным интеграционным швом;
12. Нормативную матрицу верификации сценариев `WIG-01` .. `WIG-40`.

## 2. Границы с существующей архитектурой среды выполнения (Runtime Boundary)

Реализация шлюза обязана удовлетворять каноническому Rust-интерфейсу `InternetGate`, определенному в `crates/service/src/runtime.rs` и реэкспортированному через `crates/service/src/lib.rs` (`palka_service::InternetGate`):

```rust
pub trait InternetGate: Send + Sync {
    /// Запросить фактически подтвержденное физическое состояние шлюза
    fn current_state(&self, child_sid: &str) -> Result<InternetState, PlatformError>;

    /// Запросить применение принудительной блокировки доступа в Интернет для указанного SID
    fn block_internet(&self, child_sid: &str) -> Result<(), PlatformError>;

    /// Запросить восстановление (снятие блокировки) доступа в Интернет для указанного SID
    fn unblock_internet(&self, child_sid: &str) -> Result<(), PlatformError>;
}
```

### Состояния физической фильтрации (`InternetState`)
```rust
pub enum InternetState {
    Unrestricted,
    Blocked,
    Unknown,
}
```

### Состояния готовности при запуске (`StartupReadiness`)
В соответствии с контрактами `docs/016` и `docs/017`, готовность службы при старте принимает значения:
```rust
pub enum StartupReadiness {
    Ready(StatusSnapshot),
    Degraded(StatusSnapshot),
}
```
Вариант `StartupReadiness::Fatal` **ОТСУТСТВУЕТ**. Фатальный сбой инициализации возвращается как `Err(ServiceRuntimeError)`.

### Статус `PlatformError` и таксономия ошибок
В текущем репозитории `PlatformError` определен как строковая обертка сервисного уровня:
```rust
pub struct PlatformError {
    pub reason: String,
}
```
Настоящий контракт явным образом фиксирует, что текущая структура `PlatformError` является сервисной оберткой. Внутренняя реализация платформенного адаптера Windows обязана использовать типизированную таксономию ошибок `WindowsWfpError` (см. раздел 16), сохраняя нативные коды Win32/WFP. Производственный адаптер Windows выполняет сопоставление (mapping) внутренних вариантов `WindowsWfpError` в сервисный тип `PlatformError` до тех пор, пока отдельный авторизованный жизненный цикл не изменит сервисный контракт ошибок.

## 3. Архитектурные инварианты сетевой подсистемы

Будущее расположение реализации: крейт `palka-windows-platform`.

```text
[Интеграционные инварианты WFP V1]
KERNEL_CALLOUT_DRIVER_REQUIRED: NO
ENGINE_SESSION_MODEL:           NON_DYNAMIC
FWPM_SESSION_FLAG_DYNAMIC:      FORBIDDEN (MUST NOT BE SET)
TRANSACTION_MODEL:              EXPLICIT_BFE_TRANSACTIONS
HEADER:                         fwpmu.h
IMPORT_LIBRARY:                 Fwpuclnt.lib
DLL:                            Fwpuclnt.dll
```

### 3.1. Отказ от драйвера режима ядра (Kernel Callout Driver)
Для реализации блокировки исходящего и входящего сетевого трафика учетной записи ребенка в V1 **НЕ ТРЕБУЕТСЯ** разработка драйвера режима ядра WFP (Callout Driver / NDIS Filter). Все необходимые действия по фильтрации трафика на уровне авторизации сетевых потоков реализуются через стандартные фильтры прикладного уровня WFP (ALE Management API) из пользовательского режима (user-mode) службы Windows.

### 3.2. Модель сессии BFE: Запрет динамической сессии
Служба открывает сессию управления движком фильтрации функцией `FwpmEngineOpen0`.
* Флаг `FWPM_SESSION_FLAG_DYNAMIC` (0x00000001) **СТРОГО ЗАПРЕЩЕН** (`FWPM_SESSION_FLAG_DYNAMIC: FORBIDDEN`).
* **Обоснование**: В динамической сессии WFP все созданные объекты (провайдеры, подслои, фильтры) автоматически удаляются ядром Windows при закрытии сессии или аварийном завершении процесса. В концепции безопасности PALKA принудительная блокировка доступа ребенка в Интернет **не должна исчезать** из ядра при падении или перезапуске процесса `palka-service.exe`.
* Сессия BFE конфигурируется как стандартная постоянная пользовательская сессия (`flags = 0`). Все создаваемые объекты помечаются флагом персистентности.

### 3.3. Модель транзакционности (BFE Transactions)
Все составные мутации объектов WFP (создание, удаление, восстановление набора фильтров) обязаны выполняться внутри явной транзакции BFE:
* Начало: `FwpmTransactionBegin0(engineHandle, 0)`;
* Фиксация: `FwpmTransactionCommit0(engineHandle)`;
* Откат: `FwpmTransactionAbort0(engineHandle)`.

Если любой промежуточный шаг добавления или валидации фильтров завершается ошибкой, транзакция немедленно откатывается (`FwpmTransactionAbort0`). Частичная фиксация недопустима. В случае падения процесса во время открытой транзакции BFE гарантирует автоматический откат незафиксированных изменений.

## 4. Модель владения персистентными объектами и фиксированные GUID

В V1 архитектура WFP PALKA использует трехуровневую иерархию объектов:
1. **Поставщик (Provider)**: логический владелец компонентов PALKA в BFE;
2. **Подслой (Sublayer)**: изолированный уровень арбитража политик с фиксированным весом;
3. **Фильтры (Filters)**: 4 канонических правила жесткой блокировки.

### 4.1. Замороженные канонические GUID V1
Генерация случайных GUID при старте или установке запрещена. Идентификаторы зафиксированы на постоянной основе:

```text
PALKA_WFP_PROVIDER_KEY:
{C8E542CE-D407-5540-A6CB-95B9130DE318}

PALKA_WFP_SUBLAYER_KEY:
{F7C2F54D-461B-51B5-A747-4C98ABD5FA20}

FILTER_ALE_AUTH_CONNECT_V4_KEY:
{749B417E-65FC-5D78-87BE-1783DBD1054B}

FILTER_ALE_AUTH_CONNECT_V6_KEY:
{E9AD3F66-3337-5E9B-9EED-9CBCA464A890}

FILTER_ALE_AUTH_RECV_ACCEPT_V4_KEY:
{82F7D08C-7D45-58D9-B30E-4A7EAC8AB56C}

FILTER_ALE_AUTH_RECV_ACCEPT_V6_KEY:
{8D785CDF-663F-5EA1-828D-DDABAA788C00}
```

### 4.2. Спецификация поставщика (Provider Specification)
* Структура: `FWPM_PROVIDER0`
* `providerKey`: `PALKA_WFP_PROVIDER_KEY`
* `displayData.name`: `L"PALKA Parental Control WFP Provider"`
* `displayData.description`: `L"Enforces parental control internet restrictions for configured user accounts"`
* `flags`: `FWPM_PROVIDER_FLAG_PERSISTENT` (0x00000001)
* `serviceName`: `L"PalkaService"` (привязка к системному имени службы Windows)
* `providerData`: байтовый маркер `PALKA-WFP-V1`

Провайдер указывает `serviceName = L"PalkaService"`, а системная служба `PalkaService` конфигурируется с типом запуска `SERVICE_AUTO_START`. При запуске BFE персистентные объекты, ассоциированные с данным провайдером, добавляются движком фильтрации благодаря тому, что ассоциированная служба сконфигурирована для автоматического старта. Если BFE сообщает, что канонический провайдер или фильтры отключены, метод `current_state()` не должен возвращать `Blocked`.

### 4.3. Спецификация подслоя (Sublayer Specification)
* Структура: `FWPM_SUBLAYER0`
* `subLayerKey`: `PALKA_WFP_SUBLAYER_KEY`
* `providerKey`: указатель на `PALKA_WFP_PROVIDER_KEY`
* `displayData.name`: `L"PALKA Sublayer"`
* `flags`: `FWPM_SUBLAYER_FLAG_PERSISTENT` (0x00000001)
* `weight`: `0x8000` (UINT16, средний приоритет в архитектуре подслоев Windows)

### 4.4. Спецификация фильтров (Filter Specification)
* Структура: `FWPM_FILTER0`
* `providerKey`: указатель на `PALKA_WFP_PROVIDER_KEY`
* `subLayerKey`: `PALKA_WFP_SUBLAYER_KEY`
* `flags`: `FWPM_FILTER_FLAG_PERSISTENT` (0x00000001)
* Запрет флага: `FWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT` **СТРОГО ЗАПРЕЩЕН К УСТАНОВКЕ**
* Тип веса фильтра (`weight.type`): `FWP_UINT8`
* Значение веса (`weight.uint8`): `15` (максимальный вес внутри подслоя)
* Действие (`action.type`): `FWP_ACTION_BLOCK`

Безопасность и надежность фильтрации опираются на модель жесткой блокировки (`HARD_BLOCK: YES`), а не исключительно на числовое значение веса подслоя.

## 5. Точный набор фильтров и слои ALE

Состояние принудительной блокировки (`Blocked`) реализуется ровно четырьмя каноническими фильтрами на специализированных слоях Application Layer Enforcement (ALE):

| Идентификатор фильтра | Слой фильтрации WFP | Назначение |
| :--- | :--- | :--- |
| `FILTER_ALE_AUTH_CONNECT_V4_KEY` | `FWPM_LAYER_ALE_AUTH_CONNECT_V4` | Авторизация исходящих подключений IPv4: авторизация исходящего TCP-соединения выполняется до генерации TCP SYN; для UDP/ICMP — первое применимое исходящее событие потока |
| `FILTER_ALE_AUTH_CONNECT_V6_KEY` | `FWPM_LAYER_ALE_AUTH_CONNECT_V6` | Авторизация исходящих подключений IPv6: авторизация исходящего TCP-соединения выполняется до генерации TCP SYN; для UDP/ICMP — первое применимое исходящее событие потока |
| `FILTER_ALE_AUTH_RECV_ACCEPT_V4_KEY` | `FWPM_LAYER_ALE_AUTH_RECV_ACCEPT_V4` | Авторизация входящих подключений IPv4: для входящего TCP — начальная авторизация входящего SYN / receive-accept; для UDP/ICMP — первое применимое входящее событие потока |
| `FILTER_ALE_AUTH_RECV_ACCEPT_V6_KEY` | `FWPM_LAYER_ALE_AUTH_RECV_ACCEPT_V6` | Авторизация входящих подключений IPv6: для входящего TCP — начальная авторизация входящего SYN / receive-accept; для UDP/ICMP — первое применимое входящее событие потока |

### Семантика Hard Block
* Действие фильтра: `FWP_ACTION_BLOCK`.
* Запрет флага `FWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT`: данный флаг не выставляется, что гарантирует сохранение права на блокировку (`action right`) и предотвращает переопределение решения фильтрами нижележащих подслоев или сторонними приложениями.
* Исключение лишних условий: фильтры не содержат условий по IP-адресам, диапазонам портов, протоколам, путям к исполняемым файлам, сетевым интерфейсам или профилям сетей. Любой исходящий или входящий сетевой запрос учетной записи ребенка безусловно блокируется.

## 6. Семантическая модель условия Child SID (`FWPM_CONDITION_ALE_USER_ID`)

### 6.1. Построение условия на базе дескриптора безопасности
В архитектуре Windows Filtering Platform сопоставление сетевого трафика с учетной записью пользователя на слоях ALE выполняется через условие `FWPM_CONDITION_ALE_USER_ID`. В WFP отсутствует скалярное сравнение строк SID. Фильтрация базируется на модели проверки доступа Windows:

1. Интеграционный слой конвертирует строковый `child_sid` (например, `S-1-5-21-...`) в бинарный `PSID` с помощью функции Win32 `ConvertStringSidToSidW`.
2. Формируется компактный относительный (self-relative) дескриптор безопасности (`SECURITY_DESCRIPTOR`).
3. В дискреционный список контроля доступа (DACL) дескриптора добавляется одна запись разрешения (Access Allowed ACE):
   * Субъект ACE: бинарный SID ребенка (`child_sid`).
   * Маска доступа: `FWP_ACTRL_MATCH_FILTER` (специальное право доступа WFP для сопоставления с фильтром, значение `0x00000001`).
4. Поле условия фильтра инициализируется:
   * `fieldKey`: `FWPM_CONDITION_ALE_USER_ID`
   * `matchType`: `FWP_MATCH_EQUAL`
   * `conditionValue.type`: `FWP_SECURITY_DESCRIPTOR_TYPE`
   * `conditionValue.sd`: указатель на сериализованный байтовый буфер self-relative дескриптора безопасности (`FWP_BYTE_BLOB`).

### 6.2. Разграничение дескрипторов: Условие совпадения vs Защита объекта
Настоящий контракт строго разграничивает два принципиально разных дескриптора безопасности:
* **Дескриптор сопоставления ALE (Condition Security Descriptor)**: используется в качестве значения поля `FWPM_CONDITION_ALE_USER_ID`. Его DACL содержит право `FWP_ACTRL_MATCH_FILTER` для учетной записи ребенка.
* **Дескриптор управления объектом WFP (Object Management Security Descriptor)**: защищает сам объект фильтра/провайдера/подслоя от модификации или удаления через Win32 API. В нем учетная запись ребенка **НЕ ИМЕЕТ НИКАКИХ ПРАВ**.

### 6.3. Инварианты сессий пользователя
* **Невалидный SID**: если строковый `child_sid` не может быть преобразован в валидный бинарный SID, операция немедленно возвращает типизированную ошибку `WindowsWfpError::InvalidSid`.
* **Множественные сеансы (Multi-Session)**: если учетная запись ребенка вошла в систему несколько раз (например, локальный сеанс и RDP/Fast User Switching), фильтрация применяется ко всем сеансам одновременно, так как токен доступа каждого процесса содержит один и тот же базовый SID пользователя.
* **Отсутствие активного сеанса при установке правил**: фильтры WFP устанавливаются и действуют в ядре независимо от того, выполнен ли вход пользователя в систему в данный момент. При последующем входе ребенка все его процессы немедленно подпадают под действие установленных правил.

## 7. Сетевой охват и правила исключений (Network Coverage)

В V1 блокировка учетной записи ребенка является всеобъемлющей:

1. **Типы интерфейсов**: блокировка применяется ко всем типам интерфейсов без исключения (Ethernet, Wi-Fi, мобильные адаптеры, виртуальные сетевые адаптеры VPN, софтверные мосты), которые обрабатываются сетевым стеком Windows и слоями ALE.
2. **Профили сетей**: блокировка действует одинаково во всех сетевых профилях (Domain, Private, Public).
3. **Запрет исключений LAN и Loopback**:
   * Блокировка трафика на локальные подсети (LAN) и loopback (127.0.0.1, ::1) активна для ребенка. Исключения для локальной сети или loopback **СТРОГО ЗАПРЕЩЕНЫ**, так как они создают тривиальные каналы обхода (локальные прокси-серверы, туннелирование, сторонние службы).
   * Межпроцессное взаимодействие PALKA (между `tray` и `service`) построено на базе Windows Named Pipes и не использует сетевые сокеты TCP/IP, поэтому блокировка loopback IP не нарушает работу продукта.
4. **DNS и сетевой стек**:
   * Любые прямые сетевые запросы DNS (UDP/TCP порт 53), инициированные процессами ребенка, блокируются.
   * Служба Windows DNS Client (Dnscache), исполняющаяся под учетной записью `NT AUTHORITY\NetworkService`, не блокируется фильтрами PALKA, однако резолв для ребенка становится бесполезным, так как последующие попытки установить соединение к разрешенным IP-адресам блокируются на слоях ALE.
5. **Неприкосновенность системного трафика**:
   * Сетевой трафик привилегированной службы `palka-service` (работающей под `NT AUTHORITY\SYSTEM`), трафик службы `Dnscache`, служб обновления Windows и сетевых адаптеров хоста не подпадает под условие `child_sid` и функционирует без каких-либо задержек и ограничений.
6. **Captive Portal**:
   * Доступ к сетям с обязательной авторизацией (Captive Portal) из-под учетной записи ребенка при активной блокировке заблокирован. Авторизация в публичных сетях должна осуществляться родителем (администратором системы). Исключения для Captive Portal в V1 отсутствуют.

## 8. Существующие соединения и механизм реавторизации ALE (ALE Policy-Change Reauthorization)

Для предотвращения сохранения доступа через ранее открытые соединения контракт точно фиксирует поведение сетевого стека Windows:

```text
EXISTING_FLOW_REAUTHORIZATION:   REQUIRED
KERNEL_CALLOUT_FOR_V1:           NO
CUSTOM_TCP_RST_GUARANTEE:        NO
IN_FLIGHT_PACKET_ABSOLUTE_CLAIM: NO
```

### 8.1. Семантика реавторизации потоков ALE
1. В архитектуре Windows подсистема ALE классифицирует сетевые потоки с сохранением контекста состояния (stateful authorization).
2. Добавление или удаление фильтров на затрагиваемых слоях авторизации ALE (`ALE_AUTH_CONNECT` и `ALE_AUTH_RECV_ACCEPT`) инициирует реавторизацию при смене политики ядра (policy-change reauthorization).
3. Первый последующий пакет, проходящий через существующий поток ALE, созданный на затрагиваемом слое, направляется стеком на повторную авторизацию.
4. Если фильтр жесткой блокировки PALKA (`FWP_ACTION_BLOCK`) сопоставляется с параметрами потока (Child SID), повторная авторизация отклоняется.
5. Поток ALE переводится стеком Windows в заблокированное состояние и может быть разорван (torn down).

### 8.2. Честное формулирование продуктового инварианта
1. PALKA **НЕ ГАРАНТИРУЕТ** генерацию или инъекцию специализированных пакетов `TCP RST` в сокеты системы при фиксации транзакции (для этого потребовался бы драйвер режима ядра).
2. PALKA **НЕ ДЕЛАЕТ** абсолютных утверждений в отношении пакетов или байтов, которые уже находились в очередях сетевого оборудования/стека или в передаче (in flight) до момента наступления реавторизации.
3. **Нормативный инвариант PALKA**: при прохождении первого же последующего пакета через существующий поток ALE после применения фильтров стек WFP выполняет реавторизацию, блокирует пакет правилом PALKA и прекращает дальнейший обмен данными в потоке.

## 9. Время жизни фильтров и поведение при сбоях (Filter Lifetime & Failure Scenarios)

```text
DYNAMIC_SESSION:                    NO
PROVIDER_PERSISTENT:                YES
SUBLAYER_PERSISTENT:                YES
FILTERS_PERSISTENT:                 YES
BOOT_TIME_FILTERS:                  NO
GRACEFUL_SERVICE_STOP_CALLS_UNBLOCK: NO
```

### 9.1. Штатная остановка службы Windows (Graceful Service Stop)
В полном соответствии с `docs/014`, `docs/016` и `docs/017`:
* Остановка службы `palka-service` через диспетчер SCM (сигнал `SERVICE_CONTROL_STOP`) **НЕ ВЫЗЫВАЕТ** `unblock_internet()`.
* Записанное целевое состояние `DesiredInternetState` остается неизменным.
* Персистентные фильтры блокировки остаются активными в ядре Windows. Доступ ребенка в сеть остается заблокированным во время отсутствия работающей службы.

### 9.2. Аварийное падение процесса службы (Service Process Crash)
* Аварийное завершение процесса службы (`crash`, `kill`, `OOM`) оставляет уже зафиксированные персистентные объекты WFP активными в ядре BFE, пока служба BFE продолжает работу.
* Если падение процесса службы произошло в момент выполнения транзакции изменения конфигурации WFP, механизм транзакций BFE автоматически откатывает незавершенную транзакцию до исходного валидного состояния.
* В случае перезапуска операционной системы или службы BFE персистентные объекты PALKA восстанавливаются при запуске BFE.

### 9.3. Перезапуск службы (Service Restart & Reconciliation)
При старте служба считывает сохраненное целевое состояние `DesiredInternetState` и запускает согласование:
* Если `DesiredInternetState == Blocked`: служба вызывает `block_internet(child_sid)`. Метод выполняет идемпотентную валидацию, подтверждает наличие всех четырех правил и возвращает `Ok(())`.
* Если `DesiredInternetState == Unrestricted`: служба вызывает `unblock_internet(child_sid)`. Метод удаляет блокирующие фильтры и возвращает `Ok(())`.
* Служба вызывает `current_state(child_sid)` для подтверждения физического состояния перед рапортованием статуса готовности SCM.

### 9.4. Перезагрузка Windows / Перезапуск службы BFE
* Так как провайдер, подслой и фильтры созданы с флагом `FWPM_*_FLAG_PERSISTENT`, подсистема BFE восстанавливает их из системного хранилища: персистентные объекты PALKA восстанавливаются/добавляются при запуске BFE, поскольку ассоциированная служба `PalkaService` сконфигурирована для автоматического старта (`SERVICE_AUTO_START`).
* Провайдер PALKA ассоциирован с системной службой `PalkaService` (`serviceName = L"PalkaService"`).

## 10. Алгоритм идемпотентного выполнения `block_internet()`

Метод `block_internet(child_sid)` обязан гарантировать строгое соблюдение идемпотентности:

```text
                          block_internet(child_sid)
                                     │
                     Валидация синтаксиса child_sid
                                     │
                      Открытие BFE транзакции записи
                                     │
               Проверка наличия Provider и Sublayer PALKA
                                     │
                 ├── Отсутствуют ──► Создание с флагом PERSISTENT
                 └── Присутствуют ─► Валидация канонических параметров
                                     │
                 Проверка наличия 4-х канонических фильтров
                                     │
  ┌──────────────────────────────────┼──────────────────────────────────┐
  ▼                                  ▼                                  ▼
Все 4 фильтра валидны        Частичный набор фильтров           Фильтры отсутствуют
и настроены на текущий SID   (или несовпадение SID)                     │
  │                                  │                                  │
Возврат Ok(()) без дублей     Транзакционное удаление            Создание всех 4-х
(Commit транзакции)          поврежденных фильтров              фильтров в транзакции
                                     │                                  │
                                     └────────────────► ◄───────────────┘
                                                        │
                                            Фиксация транзакции BFE
                                                        │
                                                   Возврат Ok(())
```

### Пограничные ситуации и конфликты владения
1. **Коллизия GUID с чужим объектом**: если канонический GUID занят объектом, не принадлежащим провайдеру `PALKA_WFP_PROVIDER_KEY`, удаление чужого объекта **СТРОГО ЗАПРЕЩЕНО**. Метод откатывает транзакцию и возвращает ошибку `WindowsWfpError::OwnershipConflict`.
2. **Неожиданные фильтры PALKA**: если обнаружены посторонние фильтры, привязанные к провайдеру PALKA, транзакция прерывается с ошибкой `WindowsWfpError::InconsistentState` для предотвращения неконтролируемых модификаций.

## 11. Алгоритм идемпотентного выполнения `unblock_internet()`

Метод `unblock_internet(child_sid)` переводит систему в разрешенное состояние:

1. Открывается явная транзакция записи BFE.
2. Выполняется поиск канонических фильтров по их 4-м GUID.
3. **Если фильтры отсутствуют**: транзакция фиксируется, возвращается `Ok(())`.
4. **Если обнаружены канонические фильтры**:
   * Выполняется проверка владения (`providerKey == PALKA_WFP_PROVIDER_KEY`).
   * Фильтры удаляются функцией `FwpmFilterDeleteByKey0`.
   * Даже если параметры фильтра (например, привязанный SID) устарели или повреждены, канонический фильтр PALKA удаляется, обеспечивая снятие блокировки.
5. **Инфраструктурные объекты**: Провайдер (`PALKA_WFP_PROVIDER_KEY`) и Подслой (`PALKA_WFP_SUBLAYER_KEY`) **НЕ УДАЛЯЮТСЯ**. Они остаются постоянной инфраструктурой сетевой подсистемы PALKA.
6. **Конфликты**: Чужие фильтры сторонних провайдеров никогда не удаляются. При наличии посторонних фильтров под провайдером PALKA возвращается `WindowsWfpError::InconsistentState`.
7. Транзакция фиксируется, метод возвращает `Ok(())`.

## 12. Семантика истинности наблюдаемого состояния `current_state()`

Метод `current_state(child_sid)` опрашивает BFE в режиме реального времени.

Запрещено возвращать закешированное значение, сохраненное значение `DesiredInternetState` или результат предыдущего вызова.

### Таблица истинности наблюдаемого состояния

Каноническое разграничение состояний физической фильтрации:
* ровно 0 блокирующих фильтров PALKA при отсутствии поврежденных/неожиданных объектов PALKA => `InternetState::Unrestricted`;
* ровно 4 канонических валидных фильтра (2 Connect + 2 Recv/Accept) => `InternetState::Blocked`;
* частичный канонический набор из 1, 2 или 3 фильтров => `InternetState::Unknown`.

| Фильтры V4/V6 Connect | Фильтры V4/V6 Recv/Accept | Провайдер / Подслой | Соответствие SID | Состояние флагов | Итог `current_state` |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Присутствуют (2) | Присутствуют (2) | Валидны (PALKA) | Точное совпадение | Все 4 активны, Hard Block | `InternetState::Blocked` |
| Отсутствуют (0) | Отсутствуют (0) | Валидны / Отсутствуют | N/A | Нет фильтров PALKA | `InternetState::Unrestricted` |
| Частичный набор (суммарно 1, 2 или 3 фильтра) | Любое | Любое | Любое | Нарушена целостность | `InternetState::Unknown` |
| Присутствуют (2) | Присутствуют (2) | Чужой провайдер/подслой | Любое | Коллизия объектов | `InternetState::Unknown` |
| Присутствуют (2) | Присутствуют (2) | Валидны | Не совпадает с child_sid | Старый/чужой SID | `InternetState::Unknown` |
| Присутствуют (2) | Присутствуют (2) | Валидны | Точное совпадение | Выставлен `CLEAR_ACTION_RIGHT` | `InternetState::Unknown` |
| Присутствуют (2) | Присутствуют (2) | Провайдер/фильтр отключен | Любое | Отключен в BFE | `InternetState::Unknown` |
| Ошибка вызова BFE | Любое | Любое | Любое | Сбой Win32 API / RPC | `Err(PlatformError)` |

`InternetState::Unrestricted` фиксирует исключительно факт отсутствия активных блокировок PALKA. Данный статус не гарантирует наличия физического подключения кабеля, корректности настроек DNS роутера или разрешений сторонних брандмауэров.

## 13. Модель дескрипторов безопасности объектов WFP (Object Security Model)

Для защиты сетевых правил от модификации или удаления ребенком, работающим под стандартной учетной записью Windows (Standard User):

1. **Запрет прав непривилегированного пользователя**: учетной записи ребенка не предоставляется никаких прав на управление объектами WFP (`FWPM_ACTRL_WRITE`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER`).
2. **Канонический SDDL дескриптора управления**:
   Объекты провайдера, подслоя и фильтров создаются с дескриптором безопасности, предоставляющим полный доступ только системной учетной записи (`SYSTEM`) и группе встроенных администраторов (`BUILTIN\Administrators`):
   ```text
   D:P(A;;GA;;;SY)(A;;GA;;;BA)
   ```
   * `D:P` — защищенный DACL (Protected, блокирует наследование родительских прав);
   * `(A;;GA;;;SY)` — Access Allowed, Generic All (`GA`) для `NT AUTHORITY\SYSTEM` (`SY`);
   * `(A;;GA;;;BA)` — Access Allowed, Generic All (`GA`) для `BUILTIN\Administrators` (`BA`).
3. Дескриптор безопасности управления объектом (`PSECURITY_DESCRIPTOR`) передается в качестве отдельного аргумента `sd` / `pSD` при вызове функций добавления объектов (`FwpmProviderAdd0`, `FwpmSubLayerAdd0`, `FwpmFilterAdd0`). Он не является полем структур `FWPM_PROVIDER0`, `FWPM_SUBLAYER0`, `FWPM_FILTER0`.
4. Вызов функций модификации безопасности `Fwpm*SetSecurityInfo0` внутри явных транзакций BFE запрещен спецификацией Microsoft. Дескриптор формируется и передается строго при конструировании объекта.
5. Продукт защищает систему в рамках модели безопасности стандартного пользователя и явным образом не декларирует защиту от локального администратора, имеющего права на остановку службы BFE или модификацию реестра ядра.

## 14. Модель угроз V1 (Threat Model)

### 14.1. Векторы атак, парируемые в V1
* Попытка ребенка использовать альтернативные браузеры, консольные утилиты (`curl`, `powershell`), торрент-клиенты, сторонние игры.
* Попытка ребенка установить соединение по протоколу IPv6 при наличии блокировки IPv4 (оба протокола жестко заблокированы).
* Попытка запуска локального прокси-сервера или туннеля через loopback/LAN (трафик loopback/LAN заблокирован).
* Множественный параллельный вход под одной учетной записью.
* Перезапуск пользовательских процессов или выход/вход в сеанс Windows.
* Попытка удаления фильтров WFP через стандартные пользовательские API без повышения привилегий.

### 14.2. Векторы, находящиеся вне модели угроз V1
* Повышение привилегий до локального администратора (`BUILTIN\Administrators`) или `NT AUTHORITY\SYSTEM`.
* Загрузка вредоносного неподписанного драйвера режима ядра (компрометация ring 0).
* Изменение системного времени или конфигурации BFE из-под учетной записи администратора.
* Физический доступ к жесткому диску с загрузкой другой операционной системы (LiveUSB) в обход шифрования BitLocker.

## 15. Производственная политика повторных попыток (`InternetRetryPolicy`)

Настоящий контракт является владельцем канонических параметров и алгоритма `InternetRetryPolicy`:

```text
[Константы политики повторов]
INITIAL_DELAY_SECONDS: 1
MULTIPLIER:            2
MAXIMUM_DELAY_SECONDS: 60
JITTER:                NONE
```

### 15.1. Формула расчета задержки
Для номера попытки `attempt_count >= 1`:
```text
delay = min(1s * 2^(attempt_count - 1), 60s)
```
Для обеспечения абсолютной полноты и детерминированности: при `attempt_count == 0` вычисление приравнивается к попытке 1 и возвращает ровно `1` секунду.

### 15.2. Каноническая последовательность задержек (секунды)
Нормальная последовательность задержек, начиная с первой попытки (`attempt_count = 1`):
```text
1, 2, 4, 8, 16, 32, 60, 60, ...
```

Полная таблица значений (включая защитную обработку `attempt_count = 0`):
```text
Попытка (attempt_count):  0   1   2   3   4    5    6    7    8   ...
Задержка (секунды):       1   1   2   4   8   16   32   60   60   ...
```

### 15.3. Свойства политики
* Все значения строго детерминированы, монотонно неубывают и ограничены сверху потолком в 60 секунд.
* Политика не содержит вызовов `std::thread::sleep`, циклов ожидания или зависимостей от системных часов.
* Вычисление является чистой функцией, возвращающей `std::time::Duration`. Планирование пробуждения принадлежит управляющему циклу `ServiceRuntime`.

## 16. Типизированная таксономия ошибок сетевой платформы

Для устранения текущего ограничения `PlatformError { reason: String }` будущая реализация модуля `palka-windows-platform` обязана реализовать структурированную таксономию ошибок:

```rust
#[derive(Debug)]
pub enum WindowsWfpError {
    UnsupportedPlatform,
    InvalidSid { sid: String, win32_code: u32 },
    EngineUnavailable { win32_code: u32 },
    AccessDenied { win32_code: u32 },
    TransactionBeginFailure { win32_code: u32 },
    TransactionCommitFailure { win32_code: u32 },
    TransactionAbortFailure { win32_code: u32 },
    ProviderQueryFailure { win32_code: u32 },
    SublayerQueryFailure { win32_code: u32 },
    FilterQueryFailure { win32_code: u32 },
    FilterEnumerationFailure { win32_code: u32 },
    ProviderMutationFailure { win32_code: u32 },
    SublayerMutationFailure { win32_code: u32 },
    FilterAddFailure { win32_code: u32 },
    FilterDeleteFailure { win32_code: u32 },
    OwnershipConflict { key: &'static str },
    InconsistentState { details: &'static str },
}
```

Все нативные коды Win32/WFP/RPC сохраняются в виде числовых полей `win32_code`. Диагностические сообщения и строковые представления не содержат секретов и токенов.

Производственный адаптер Windows преобразует варианты `WindowsWfpError` в сервисный тип `PlatformError { reason: String }` (сохраняя диагностический контекст и код ошибки) до тех пор, пока отдельный этап жизненного цикла не изменит контракт сервисного интерфейса.

## 17. Архитектура тестируемости (Testability Seam)

Для изоляции модульных тестов от вызовов реального BFE крейт `palka-windows-platform` проектируется с локальным абстрактным швом:

```rust
pub trait WfpEnginePort: Send + Sync {
    fn open_engine(&mut self) -> Result<(), WindowsWfpError>;
    fn close_engine(&mut self);
    fn transaction_begin(&mut self) -> Result<(), WindowsWfpError>;
    fn transaction_commit(&mut self) -> Result<(), WindowsWfpError>;
    fn transaction_abort(&mut self) -> Result<(), WindowsWfpError>;
    fn provider_exists(&self, key: &Guid) -> Result<bool, WindowsWfpError>;
    fn add_provider(&mut self, provider: &WfpProviderSpec) -> Result<(), WindowsWfpError>;
    fn sublayer_exists(&self, key: &Guid) -> Result<bool, WindowsWfpError>;
    fn add_sublayer(&mut self, sublayer: &WfpSubLayerSpec) -> Result<(), WindowsWfpError>;
    fn filter_exists(&self, key: &Guid) -> Result<bool, WindowsWfpError>;
    fn get_filter(&self, key: &Guid) -> Result<Option<WfpFilterSpec>, WindowsWfpError>;
    fn add_filter(&mut self, filter: &WfpFilterSpec) -> Result<(), WindowsWfpError>;
    fn delete_filter(&mut self, key: &Guid) -> Result<(), WindowsWfpError>;
    fn enumerate_provider_filters(&self, provider_key: &Guid) -> Result<Vec<WfpFilterSpec>, WindowsWfpError>;
}
```

* **Модульные тесты**: используют тестовую реализацию `FakeWfpEnginePort` в оперативной памяти. Никакие Win32 API не вызываются, права администратора не требуются, сетевой стек разработчика не подвергается модификациям.
* **Интеграционные тесты Windows**: выполняются строго в изолированной тестовой среде (виртуальная машина Windows) с выделенной тестовой учетной записью ребенка и обязательной очисткой созданных правил в блоке финализации теста.

| **WIG-09** | Множественные сеансы ребенка | При наличии двух активных сеансов одной учетной записи трафик блокируется в обоих сеансах. |
| **WIG-10** | Отложенный вход ребенка в систему | Фильтры, установленные до входа пользователя в систему, немедленно блокируют трафик при последующем входе. |
| **WIG-11** | Идемпотентность `block_internet()` | Повторный вызов `block_internet()` при наличии канонических фильтров завершается успехом без создания дубликатов. |
| **WIG-12** | Идемпотентность `unblock_internet()` | Повторный вызов `unblock_internet()` при отсутствии фильтров завершается успехом `Ok(())`. |
| **WIG-13** | Транзакционное восстановление фильтров | При наличии неполного набора канонических фильтров метод `block_internet()` атомарно восстанавливает недостающие. |
| **WIG-14** | Атомарный откат при сбое добавления | Сбой при добавлении 3-го фильтра приводит к откату всей транзакции BFE; частичный коммит отсутствует. |
| **WIG-15** | Падение процесса внутри транзакции | Принудительное завершение процесса службы до фиксации транзакции приводит к автоматическому отмене изменений BFE. |
| **WIG-16** | Устойчивость блокировки при падении службы | Аварийная остановка процесса `palka-service.exe` оставляет ранее зафиксированные персистентные фильтры активными в ядре. |
| **WIG-17** | Штатный останов службы без снятия фильтров | При получении `SERVICE_CONTROL_STOP` служба завершает работу без вызова `unblock_internet()`. |
| **WIG-18** | Восстановление объектов при запуске BFE | После перезагрузки ОС или службы BFE персистентные объекты PALKA восстанавливаются/добавляются при запуске BFE благодаря конфигурации `SERVICE_AUTO_START`. |
| **WIG-19** | Согласование при старте: `Desired = Blocked` | При запуске с целевым состоянием `Blocked` вызывается `block_internet()` с подтверждением через `current_state()`. |
| **WIG-20** | Согласование при старте: `Desired = Unrestricted` | При запуске с целевым состоянием `Unrestricted` вызывается `unblock_internet()` с подтверждением через `current_state()`. |
| **WIG-21** | Полный набор фильтров => `Blocked` | При наличии всех 4-х валидных фильтров с корректным SID метод `current_state()` возвращает `InternetState::Blocked`. |
| **WIG-22** | Частичный набор фильтров => `Unknown` | При наличии частичного набора (1, 2 или 3 канонических фильтра из 4-х) `current_state()` честно рапортует `Unknown` (случай ровно 0 фильтров без аномалий классифицируется как `Unrestricted`). |
| **WIG-23** | Наличие только IPv4 или только IPv6 => `Unknown` | Наличие только правил IPv4 без правил IPv6 трактуется как несогласованное состояние `Unknown`. |
| **WIG-24** | Модификация параметров фильтра => `Unknown` | Изменение веса, слоя или флагов канонического фильтра приводит к возврату `InternetState::Unknown`. |
| **WIG-25** | Неожиданные фильтры провайдера => `Unknown` | Обнаружение постороннего фильтра под провайдером PALKA приводит к статусу `InternetState::Unknown`. |
| **WIG-26** | Неприкосновенность чужих фильтров | Фильтры сторонних провайдеров никогда не удаляются методами `block_internet()` или `unblock_internet()`. |
| **WIG-27** | Коллизия GUID стороннего объекта | Попытка использования занятого чужим объектом канонического GUID завершается ошибкой `OwnershipConflict`. |
| **WIG-28** | Реавторизация существующих TCP-потоков | При прохождении первого последующего пакета через существующий TCP-поток на затрагиваемом ALE-слое выполняется реавторизация; поток блокируется фильтром PALKA и разрывается. |
| **WIG-29** | Реавторизация существующих UDP-потоков | Первый последующий UDP-пакет в существующем потоке инициирует реавторизацию на слое ALE; при совпадении с правилом PALKA пакет отклоняется и поток блокируется. |
| **WIG-30** | Невозможность переопределения Hard Block | Разрешающие фильтры в нижележащих подслоях не могут отменить блокировку из-за отсутствия флага `CLEAR_ACTION_RIGHT`. |
| **WIG-31** | Блокировка DNS-запросов ребенка | Прямой DNS-трафик учетной записи ребенка блокируется; системный резолвер службы `service` функционирует штатно. |
| **WIG-32** | Запрет обхода через Loopback и LAN | Попытки обращения к `127.0.0.1` и адресам локальной подсети блокируются каноническими фильтрами. |
| **WIG-33** | Защита от удаления стандартным пользователем | Попытка вызова `FwpmFilterDeleteByKey0` из-под токена ребенка возвращает ошибку `ERROR_ACCESS_DENIED`. |
| **WIG-34** | Защита дескриптора безопасности объекта | Попытка изменения DACL или владельца объекта WFP ребенком отклоняется подсистемой безопасности Windows. |
| **WIG-35** | Экспоненциальная шкала повторов | Задержки строго следуют ряду `1, 2, 4, 8, 16, 32, 60, 60...` секунд с максимальным ограничением 60 с. |
| **WIG-36** | Защитное поведение при нулевой попытке | При передаче `attempt_count = 0` политика повторов возвращает задержку в 1 секунду. |
| **WIG-37** | Честность при сбоях RPC/BFE | Сбой опроса BFE возвращает `Err(PlatformError)`, предотвращая ложное декларирование состояния `Blocked`. |
| **WIG-38** | Отключенное состояние провайдера или фильтров => `Unknown` | Если BFE сообщает, что канонический провайдер или фильтры отключены (включая сценарий привязки к службе / auto-start по спецификации Microsoft), `current_state()` не возвращает `Blocked`, а возвращает `Unknown` (или соответствующую платформенную ошибку запроса). |
| **WIG-39** | Обновление фильтра при смене Child SID | При изменении конфигурации SID вызов `block_internet()` атомарно заменяет условия во всех канонических фильтрах. |
| **WIG-40** | Очистка устаревших фильтров при Unrestricted | Согласование `Unrestricted` гарантированно удаляет канонические блокирующие фильтры старого SID без вреда чужим объектам. |

## 19. Вопросы, исключенные из рамок контракта (Out of Scope)

Настоящий документ регламентирует исключительно сетевую фильтрацию WFP для Windows. За рамки контракта явным образом вынесены:
1. Реализация управления питанием и питанием устройств (`PowerController` / `docs/006`);
2. Адаптер выключения системы Win32;
3. Сервисный Composition Root (`main.rs`);
4. Транспорт Telegram и протоколы сетевого взаимодействия;
5. Локальный IPC Named Pipes и интерфейс системного трея;
6. Инсталлятор продукта (WiX/MSI);
7. Драйверы режима ядра (NDIS, WFP Callout);
8. Сторонние библиотеки перехвата пакетов (WinDivert, WinPcap);
9. Автоматизация брандмауэра Windows через COM (`INetFwPolicy2`) или утилиту `netsh`;
10. Изменения файлов исходного кода Rust (`*.rs`) и манифестов `Cargo.toml`.

## 20. Граница перехода к следующему этапу жизненного цикла

Завершение настоящего этапа формирует нормативный базис для последующего этапа:

```text
NEXT_LIFECYCLE_STAGE:
WINDOWS-INTERNET-GATE IMPLEMENTATION
```

Этап реализации будет авторизован отдельной операцией и включит в себя разработку кода Rust в крейте `palka-windows-platform`, привязку к системной библиотеке `Fwpuclnt.dll` и реализацию тестовых швов.
