# Контракт тестирования (Test Contract)

Документ определяет нормативные требования к верификации контрактов, структуре тестов и обязательным интеграционным сценариям.

## 1. Иерархия тестирования (Test Hierarchy)

1. **Модульные тесты `core` (Pure Unit Tests)**:
   * Полностью детерминированные тесты конечных автоматов и математики таймеров без ввода-вывода и задержек реального времени (`std::time::Instant` абстрагируется).
   * 100% покрытие пограничных условий порогов (60m, 30m, 20m, 10m, 3m), фильтрации уже пройденных порогов, замены и отмены таймеров, а также сдвигов времени.
2. **Контрактные тесты IPC и Telegram (Contract & Protocol Tests)**:
   * Тестирование сериализации/десериализации команд и событий.
   * Тестирование строгости белых списков Telegram ID и блокировок перебора PIN.
3. **Интеграционные тесты `windows-platform` и `service` (System & Integration Tests)**:
   * Проверка взаимодействия с реальным Windows API в тестовом окружении.

## 2. Обязательные интеграционные тестовые сценарии (Mandatory Scenarios)

### 2.1. Верификация сброса установленных соединений (Established Connection Teardown Test)
* **Цель**: Доказать, что реализация `InternetGate` не просто блокирует новые попытки рукопожатия TCP SYN, но немедленно разрывает передачу данных по активным соединениям.
* **Сценарий**:
  1. В контексте учетной записи сконфигурированного пользователя (Child SID) запускается непрерывная передача данных по установленному TCP-сокету (например, загрузка потока данных или постоянный HTTP/WebSocket-стрим).
  2. Фиксируется успешная двусторонняя передача пакетов.
  3. Служба выполняет `InternetGate::block_internet(child_sid)`.
  4. **Критерий успешности**: Передача данных по открытому сокету немедленно прекращается, последующие операции чтения/записи в сокете завершаются ошибкой (Connection Reset / Aborted), а новые попытки подключения блокируются.

### 2.2. Верификация селективности и связности службы (Service Connectivity Preservation Test)
* **Цель**: Подтвердить, что блокировка интернета для Child SID не затрагивает сетевой трафик самой службы.
* **Сценарий**:
  1. Включается режим `InternetState::Blocked` для Child SID.
  2. Процесс службы `service` выполняет сетевой запрос к эндпоинту Telegram API (или тестовому HTTP/HTTPS серверу).
  3. **Критерий успешности**: Запрос службы успешно доходит до адресата и получает ответ, в то время как трафик целевого пользователя заблокирован.

### 2.3. Верификация живучести таймеров (Timer Durability & Reboot Simulation)
* **Цель**: Доказать сохранение запланированных действий при сбоях и перезагрузках.
* **Сценарий**:
  1. Устанавливается таймер на блокировку через 15 минут.
  2. Процесс `tray` принудительно завершается (SIGKILL / `TerminateProcess`).
  3. Служба `service` останавливается и перезапускается с сохранением системного времени.
  4. **Критерий успешности**: После старта служба считывает активный таймер и в нужный момент времени дедлайна инициирует блокировку через `InternetGate`.

### 2.4. Верификация просроченных дедлайнов (Missed Deadline Recovery Test)
* **Цель**: Проверить реакцию на дедлайн, наступивший во время отключенного состояния компьютера.
* **Сценарий**:
  1. Устанавливается таймер на блокировку через 10 минут.
  2. Служба останавливается.
  3. Системные виртуальные часы переводятся вперед на 20 минут (дедлайн остался в прошлом).
  4. Служба запускается.
  5. **Критерий успешности**: Служба немедленно переводит `InternetGate` в `InternetState::Blocked` без генерации устаревших промежуточных предупреждений.

### 2.5. Верификация анти-брутфорса PIN (PIN Brute-Force Rate Limiting Test)
* **Цель**: Доказать авторитетность защиты от подбора PIN в `service`.
* **Сценарий**:
  1. Через IPC отправляются 3 неверных значения PIN подряд.
  2. 4-я попытка (даже с верным PIN) отправляется немедленно.
  3. **Критерий успешности**: Служба возвращает ошибку блокировки с указанием времени ожидания таймаута; верный PIN принимается только по истечении заданного таймаута.
