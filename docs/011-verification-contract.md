# Контракт верификации (Verification Contract)

Документ определяет нормативные требования к уровням доказательств, верификационным шлюзам, классификации изменений и критериям достаточности свидетельств корректности для компонентов проекта PALKA.

## 1. Назначение и модель доверия (Purpose and Trust Model)

Настоящий контракт определяет, какие объективные свидетельства признаются необходимыми и достаточными для подтверждения корректности изменений в кодовой базе и архитектуре.

В системе верификации выделяются четыре независимых актора:
1. **Архитектор / Аудитор (Architect / Auditor)** — независимый субъект, определяющий архитектурные решения, формирующий авторизованные манифесты и проверяющий соответствие результатов нормативным требованиям.
2. **Исполнитель (Executor / Antigravity)** — агент или разработчик, выполняющий предписанные команды строго в рамках выданных полномочий.
3. **Удаленный репозиторий GitHub / Объектная база Git (GitHub Remote / Git Object Database)** — авторитарный источник неизменяемых Git-объектов, веток, коммитов и pull request'ов.
4. **Независимый верификатор CI (Independent CI Verifier)** — изолированная среда непрерывной интеграции (GitHub-hosted clean runners), независимо проверяющая целостность и корректность кода.

### Фундаментальный нормативный инвариант
> **ВЫВОД ИСПОЛНИТЕЛЯ НИКОГДА НЕ ЯВЛЯЕТСЯ ДОСТАТОЧНЫМ ДОКАЗАТЕЛЬСТВОМ САМ ПО СЕБЕ (EXECUTOR OUTPUT IS NEVER SUFFICIENT PROOF BY ITSELF).**

* Текстовые отчеты и утверждения Исполнителя **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНЫ (MUST NOT)** приниматься в качестве доказательств без приложения проверяемых первичных (сырых) машинных свидетельств.
* Для любых изменений исходного кода после завершения раскрутки CI (CI bootstrap) локальные свидетельства Исполнителя сами по себе **КАТЕГОРИЧЕСКИ НЕ ЯВЛЯЮТСЯ ДОСТАТОЧНЫМИ (MUST NOT BE SUFFICIENT)** для принятия изменений.

## 2. Уровни доказательств V0–V5 (Evidence Levels V0–V5)

В системе устанавливаются шесть дискретных уровней доказательств:

| Уровень | Наименование | Описание и состав свидетельств |
| :--- | :--- | :--- |
| **V0** | **Git Object Evidence** | Неизменяемые факты объектной базы Git: SHA коммита, упорядоченные родители (`parent SHA`), хэш дерева (`tree SHA`), точный список измененных файлов, полный diff, удаленные ссылки (`origin/main`, `origin/feature`). |
| **V1** | **Local Execution Evidence** | Первичные машинные логи процесса исполнения на стороне Исполнителя: точные команды, аргументы, метки времени UTC, рабочий каталог (`cwd`), раздельные потоки `stdout` и `stderr`, целочисленный код возврата (`exit code`), предусловия, постусловия, результаты локальных тестов. |
| **V2** | **Independent Clean-Room CI** | Результаты независимой проверки точного коммита/PR на чистых изолированных раннерах GitHub Actions в изолированном окружении. Локальное окружение Исполнителя **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНО (MUST NOT)** приравниваться к среде CI. |
| **V3** | **Windows Integration Evidence** | Свидетельства исполнения в реальной среде ОС Windows, подтверждающие корректность взаимодействия с Windows API и механизмами безопасности (файловая система, DACL/ACL, Windows DPAPI, Named Pipes, интерфейсы Windows Service, платформенные адаптеры). |
| **V4** | **Privileged / Destructive Windows E2E Evidence** | Свидетельства из изолированной виртуальной машины / эфемерного Windows-раннера (`ephemeral`), подтверждающие привилегированное, деструктивное или требующее перезагрузки поведение: пакетная фильтрация WFP для Child SID, мгновенный сброс активных TCP-соединений, восстановление службы после рестарта, восстановление после перезагрузки ОС, жизненный цикл выключения питания, проверка эффективных прав ACL, автономность службы при завершении процесса трея. |
| **V5** | **Release Provenance Evidence** | Криптографически проверяемая связь релизного бинарного артефакта с исходным кодом: SHA коммита, идентификатор CI workflow, хэши SHA-256 артефактов, спецификация компонентов (SBOM), аттестация цепочки поставок (Artifact Attestation). **V5 подтверждает подлинность и происхождение сборки, но не гарантирует автоматически отсутствие уязвимостей в логике.** |

## 3. Классы изменений и матрица доказательств (Change Classes & Evidence Matrix)

Все вносимые в репозиторий изменения классифицируются по категориям риска:

1. **`DOC`** — изменения исключительно в документации репозитория (`docs/**`, `README.md`).
2. **`CORE`** — чистая логика домена и конечных автоматов в `crates/core`.
3. **`SERVICE_LOGIC`** — бизнес-логика службы, оркестрация таймеров и подсистем.
4. **`PERSISTENCE`** — структуры долговременного хранения, сериализация, атомарная запись файлов состояния, DPAPI.
5. **`WINDOWS_PLATFORM`** — платформенные адаптеры, взаимодействие с Win32 API, WFP, Power Management, Windows Service.
6. **`SECURITY_CRITICAL`** — подсистемы авторизации (PIN, Telegram whitelist), криптография (Argon2id, DPAPI), списки доступа DACL, Named Pipe security, изоляция привилегий.
7. **`CI_GOVERNANCE`** — конфигурация рабочих процессов CI (`.github/**`), скрипты управления, манифесты и правила верификации.
8. **`RELEASE`** — релизные сборки, теги версий, дистрибутивы.

### Нормативная матрица требуемых уровней доказательств

| Класс изменения | Минимальный требуемый уровень доказательств | Дополнительные условия |
| :--- | :--- | :--- |
| **`DOC`** | **V0 + V1** | После развертывания CI — также применимый шлюз V2 (линтеры, проверка ссылок). |
| **`CORE`** | **V0 + V1 + V2** | Обязательные детерминированные тесты конечных автоматов в clean-room CI. |
| **`SERVICE_LOGIC`** | **V0 + V1 + V2** | **+ V3** при затрагивании механизмов реального рантайма Windows. |
| **`PERSISTENCE`** | **V0 + V1 + V2** | **+ V3** для интеграции с Windows DPAPI, файловой системой и проверкой атомарности замещения. |
| **`WINDOWS_PLATFORM`** | **V0 + V1 + V2 + V3** | Обязательное подтверждение взаимодействия с реальным Windows API. |
| **`SECURITY_CRITICAL`** | **V0 + V1 + V2 + V3** | **+ V4** перед финальным приемом изменений, требующих привилегий SYSTEM, разрыва сетевых потоков, управления питанием или перезагрузки. |
| **`CI_GOVERNANCE`** | **V0 + V1 + Аудит** | Независимый аудит Архитектора. Кандидатный верификатор **КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН** считаться доказательством собственной корректности лишь потому, что он сообщает об успехе. После bootstrap — выполнение существующих/кандидатных проверок CI. |
| **`RELEASE`** | **V0 + V1 + V2 + V3 + V4 + V5** | Полный профиль доказательств, включая криптографическую аттестацию происхождения бинарных файлов. |

## 4. Исключение самораскрутки (Bootstrap Exception)

В проекте устанавливается строго ограниченное исключение начальной раскрутки:
* **Идентификатор режима**: **`BOOTSTRAP ONLY`**.
* **Условия действия**: До тех пор, пока инструментарий CI и управления исполнением DEC-003 не реализован и не слит в ветку `main`, изменения этапа раскрутки **МОГУТ (MAY)** временно приниматься на основе:
  1. Доказательств уровня **V0** (Git-объекты);
  2. Первичных доказательств уровня **V1** (машинные логи Исполнителя);
  3. Независимой проверки удаленного состояния Git Архитектором/Аудитором.
* **Срок действия**: Настоящее исключение **ОБЯЗАНО ИСТЕЧЬ (MUST EXPIRE)** немедленно после внедрения соответствующего верификатора.
* **Запрет постоянного обхода**: Исключение самораскрутки **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНО (MUST NOT)** превращаться в постоянный механизм обхода верификации.

## 5. Прослеживаемость контрактов в тесты (Contract → Test Traceability)

* Каждое нормативное машиночитаемое требование категорий MUST / SHALL **ДОЛЖНО (SHOULD)** явно прослеживаться к:
  * конкретному числовому/именованному идентификатору теста;
  * сценарию интеграционного тестирования;
  * автоматизированной проверке политики репозитория;
  * либо содержать задокументированное обоснование временной невозможности автоматической проверки.
* **Негативные требования (Negative Requirements)**:
  * Негативные нормативные требования **ОБЯЗАНЫ иметь негативные автоматизированные тесты ТАМ, ГДЕ ЭТО ТЕХНИЧЕСКИ ВОЗМОЖНО (WHERE TECHNICALLY POSSIBLE)**.
  * Например, требование «просроченный таймер выключения компьютера НЕ ДОЛЖЕН повторно исполняться» требует теста, подтверждающего, что счетчик вызовов `PowerController::initiate_shutdown` строго равен нулю (`count == 0`).
  * Если автоматизированная негативная проверка в настоящее время технически невозможна, запись прослеживаемости контракта/теста **ОБЯЗАНА зафиксировать**:
    1. точную причину, почему автоматизация сейчас невозможна;
    2. требуемый будущий уровень интеграционных/E2E свидетельств (V3/V4).

## 6. Таксономия тестов (Test Taxonomy)

В кодовой базе PALKA выделяются следующие категории тестов:
1. **Модульные тесты (Unit Tests)** — изолированная проверка функций и типов данных без ввода-вывода.
2. **Контрактные тесты (Contract Tests)** — детерминированная проверка сериализации, протоколов и конечных автоматов с виртуальным временем.
3. **Тесты конечных автоматов и свойств (Property / State-Machine Tests)** — проверка инвариантов на случайных последовательностях команд с фиксацией seed.
4. **Интеграционные тесты (Integration Tests)** — сквозная проверка взаимодействия модулей в пользовательском пространстве.
5. **Тесты интеграции с Windows (Windows Integration Tests)** — взаимодействие с реальными примитивами Windows (DACL, DPAPI, Named Pipes, реестр).
6. **Тесты восстановления и внедрения сбоев (Recovery / Fault-Injection Tests)** — имитация аварийных остановок, некорректных файлов состояния и рассинхронизации.
7. **Тесты безопасности и негативные сценарии (Security / Negative Tests)** — попытки неавторизованного доступа, брутфорс PIN, подделка токенов.
8. **Привилегированные сквозные тесты (Privileged E2E Tests)** — изоляция в виртуальной машине для проверки фильтрации трафика WFP и управления питанием.

## 7. Детерминизм тестирования (Determinism)

* Все тесты, используемые в качестве доказательств корректности, **ОБЯЗАНЫ быть детерминированными (MUST BE DETERMINISTIC)**.
* Системное время (wall-clock), сетевые взаимодействия и псевдослучайные генераторы для модульных и контрактных тестов **ДОЛЖНЫ контролироваться, фиксироваться сидами (seeded) либо изолироваться моками**.
* При падении тестов свойств (property tests) генератор **ОБЯЗАН** логировать конкретное упавшее значение и сид генератора (`failing seed / case`) для воспроизведения.

## 8. Политика сбоев и нестабильных тестов (Failure and Flake Policy)

* Сбой любого обязательного теста или проверки является **однозначным провалом (FAILURE)** верификации.
* **КАТЕГОРИЧЕСКИ ЗАПРЕЩАЕТСЯ** циклический перезапуск упавших проверок «до первого зеленого статуса».
* Любой повторный запуск (RERUN) требует предварительной классификации причины сбоя:
  1. `PRODUCT_FAILURE` — ошибка в коде продукта (требуется исправление кода);
  2. `TEST_FAILURE` — ошибка или нестабильность в коде теста (требуется исправление теста);
  3. `INFRASTRUCTURE_FAILURE` — независимый сбой инфраструктуры раннера / сети (только в этом случае допускается авторизованный перезапуск).
* Первичные свидетельства сбоя **ОБЯЗАНЫ оставаться доступными** в истории проверок.

## 9. Правило разрешения конфликтов доказательств (Evidence Conflict Rule)

При обнаружении расхождений между различными источниками свидетельств устанавливается строгий порядок приоритета авторитетности:

1. **Неизменяемые факты объектной базы Git и удаленного сервера GitHub** имеют безусловный наивысший приоритет над любыми отчетами Исполнителя.
2. **Первичные машинные логи выполнения (raw command evidence: stdout, stderr, exit code)** имеют безусловный приоритет над сводными файлами `README.txt` или `summary.json`.
3. Если текстовое резюме (summary/README) противоречит первичным машинным логам:
   * артефакт признается **НЕСООТВЕТСТВУЮЩИМ ТРЕБОВАНИЯМ (NONCOMPLIANT)**;
   * запрещается неявный выбор «удобного» значения в пользу успеха.

## 10. Критерии завершенности (Definition of Done)

Изменение признается полностью завершенным (**DONE**) исключительно при одновременном выполнении условий:
1. **Все проверки верификации, применимые к данному классу изменений, успешно пройдены**, включая проверки сборки, форматирования, линтеров и тестов там, где это применимо (для чистого изменения `DOC` требуются применимые проверки документации и политик, без искусственного требования компиляции кода Rust, если код не затрагивался);
2. Собраны все уровни доказательств, предусмотренные матрицей для данного класса изменений;
3. Все нормативные тесты и проверки завершились с кодом 0;
4. Произведен успешный независимый аудит со стороны Архитектора/Аудитора;
5. Неизменяемые ссылки зафиксированы в авторитарном удаленном репозитории.
