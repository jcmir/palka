# Контракт управления исполнением (Execution Governance Contract)

Документ определяет нормативные правила авторизации, поэтапного выполнения, сбора машинных свидетельств и контроля целостности процессов разработки в проекте PALKA.

## 1. Роли и распределение полномочий (Roles and Authority)

Процесс разработки и внесения изменений строго разделен между следующими ролями:
1. **Архитектор / Аудитор (Architect / Auditor)**:
   * единолично авторизует цели, манифесты и границы операций;
   * проводит независимый аудит предоставленных машинных артефактов и состояния удаленного репозитория;
   * принимает решения о слиянии или отклонении изменений.
2. **Исполнитель (Executor / Antigravity)**:
   * строго следует предписанному авторизованному манифесту операции;
   * **КАТЕГОРИЧЕСКИ НЕ ИМЕЕТ ПРАВА (MUST NOT)** самостоятельно расширять область полномочий, придумывать недекларированные действия или менять параметры среды;
   * фиксирует полные машинные свидетельства выполнения каждой команды.
3. **Независимый верификатор CI (Independent CI)**:
   * независимо исполняет чистую сборку и проверку тестов на изолированных раннерах.
4. **Удаленный репозиторий GitHub (GitHub Remote)**:
   * является единственным авторитарным источником истинного состояния веток и коммитов.

## 2. Принцип «Одна операция за раз» (One Operation at a Time)

Любая деятельность в репозитории разделяется на изолированные нормативные этапы:
* `DOCUMENTATION_IMPLEMENTATION` — создание или редактирование нормативных документов;
* `IMPLEMENTATION` — реализация или изменение исходного кода;
* `COMMIT` — создание локального Git-коммита;
* `PUSH` — отправка зафиксированного коммита в удаленный репозиторий;
* `PR_CREATE` — открытие Pull Request;
* `CI_INSPECTION` — аудит статусов и логов непрерывной интеграции;
* `RERUN` — повторный запуск упавших проверок CI при обоснованном инфраструктурном сбое;
* `MERGE` — авторизованное стандартное слияние PR;
* `GOVERNANCE_SYNC` — локальная синхронизация ветки `main` после слияния;
* `REPOSITORY_POLICY_CHANGE` — изменение настроек репозитория или правил защиты веток (rulesets);
* `RELEASE` — публикация релизных сборок и тегов.

### Правило границ этапов:
* Единоразовая авторизация **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНА (MUST NOT)** неявно пересекать границы этапов.
* Создание новой ветки **МОЖЕТ (MAY)** входить в состав явно авторизованной операции этапа `IMPLEMENTATION` или `DOCUMENTATION_IMPLEMENTATION`.

## 3. Манифест операции V1 (Operation Manifest V1)

Каждая выполняемая операция описывается строгим структурированным манифестом (`Operation Manifest V1`).

### Модель ветвления и переходов (Branch Transition Model)
Манифест явным образом разделяет три понятия веток:
1. **`expected_start_branch`** — ветка, которая **ОБЯЗАНА (MUST)** быть активной на момент проверки предполетного барьера мутаций;
2. **`target_branch`** — ветка, которая **ОБЯЗАНА (MUST)** стать активной после явного выполнения авторизованного перехода или создания ветки;
3. **`branch`** — каноническая рабочая ветка операции после выполнения любого авторизованного перехода (для операций без перехода веток значения `expected_start_branch`, `target_branch` и `branch` строго совпадают).

* Для операции, создающей функциональную ветку:
  * `expected_start_branch` = `"main"`;
  * `target_branch` = `"docs/dec-003-verification-governance-contracts"`;
  * `branch` = `"docs/dec-003-verification-governance-contracts"`.
* Манифест содержит явную политику перехода веток `branch_transition`.

### Концептуальная схема манифеста V1:
```json
{
  "manifest_version": 1,
  "operation_id": "DEC-003-PHASE-1-CONTRACTS",
  "repository": "jcmir/palka",
  "working_directory": "C:\\PALKA",
  "stage": "DOCUMENTATION_IMPLEMENTATION",
  "expected_start_branch": "main",
  "target_branch": "docs/dec-003-verification-governance-contracts",
  "branch": "docs/dec-003-verification-governance-contracts",
  "branch_transition": {
    "allowed": true,
    "mode": "create",
    "from": "main",
    "to": "docs/dec-003-verification-governance-contracts"
  },
  "expected_head": "889c96303c2e4a990362a913387ae1d6369076b5",
  "expected_base": "889c96303c2e4a990362a913387ae1d6369076b5",
  "expected_remote_refs": {
    "origin/main": "889c96303c2e4a990362a913387ae1d6369076b5"
  },
  "authorized_paths": [
    "docs/011-verification-contract.md",
    "docs/012-execution-governance-contract.md",
    "docs/013-ci-contract.md"
  ],
  "forbidden_paths": [
    "Cargo.toml", "Cargo.lock", "crates/**", ".github/**"
  ],
  "required_preconditions": [ ... ],
  "authorized_commands": [ ... ],
  "required_postconditions": [ ... ],
  "artifact_profile": "bootstrap_zip_v1",
  "stop_conditions": [ ... ]
}
```

Если переход ветки не авторизован, указывается `"branch_transition": { "allowed": false }`.

Манифест является **неизменяемым (immutable)** на все время выполнения операции. Любое изменение требований требует отдельного нового манифеста.

## 4. Предполетный барьер мутаций (Preflight Mutation Barrier)

Абсолютно любая операция с потенциальной мутацией состояния репозитория или удаленного сервера подчиняется правилу барьера:
1. До выполнения любых мутирующих команд Исполнитель обязан собрать полную информацию о предусловиях.
2. Барьер **ОБЯЗАН проверить `expected_start_branch` ДО выполнения любых действий с ветками**. Исполнитель **КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН (MUST NOT)** считать целевую ветку `target_branch` выполненным предусловием до запуска санкционированного создания ветки.
3. Вызов `git fetch origin` **РАЗРЕШАЕТСЯ (MAY)** в качестве подготовительного обновления локального кэша удаленных ссылок до проверки барьера.
4. Если хотя бы одно предусловие не совпадает с манифестом:
   * исполнение **НЕМЕДЛЕННО ОСТАНАВЛИВАЕТСЯ (STOP)** до выполнения первой мутации;
   * **КАТЕГОРИЧЕСКИ ЗАПРЕЩАЮТСЯ** неявные попытки «исправить ситуацию» (автоматический checkout другой ветки, неавторизованный git pull, reset, rebase или откат файлов).

## 5. Состояние «Уже выполнено» (ALREADY_SATISFIED State)

* Если и только если полное требуемое постусловие операции уже истинно до начала ее выполнения (например, удаленная ветка уже содержит целевой коммит, или локальный `main` уже синхронизирован с `origin/main`):
  * Исполнитель **НЕ ВЫПОЛНЯЕТ** мутирующих действий;
  * возвращается статус **`ALREADY_SATISFIED`**.
* Состояние `ALREADY_SATISFIED` принципиально отличается от `COMPLETED` и **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНО (MUST NOT)** представляться так, будто мутирующая команда была исполнена в текущей операции.

## 6. Модель результатов и состояние мутации (Result Model & Mutation State)

В процессе выполнения фиксируются статус результата (`RESULT`) и статус произведенных мутаций (`mutation_state`):

### Значения `RESULT`:
* **`COMPLETED`** — операция успешно выполнена, все предусловия и постусловия строго соблюдены;
* **`ALREADY_SATISFIED`** — целевое состояние уже было достигнуто ранее, мутаций не производилось;
* **`STOPPED`** — выполнение остановлено из-за несовпадения предусловий, сбоя команды или нарушения постусловий.

### Значения `mutation_state`:
* **`NONE`** — операция была сугубо доступной только для чтения (read-only);
* **`NOT_APPLIED`** — мутирующие команды не запускались;
* **`APPLIED`** — мутирующие команды успешно применены и подтверждены постусловиями;
* **`UNKNOWN`** — мутирующая команда была отправлена (например, `git push`), но ее окончательный статус не может быть однозначно подтвержден.

> [!IMPORTANT]
> Если мутирующая команда могла изменить удаленное или локальное состояние, но ее точный результат остался неопределенным (`mutation_state = UNKNOWN`):
> * `RESULT` устанавливается в **`STOPPED`**;
> * следующей авторизованной операцией **ОБЯЗАНА БЫТЬ ТОЛЬКО СВЕРКА В РЕЖИМЕ ЧТЕНИЯ (READ-ONLY RECONCILIATION)**;
> * повторные мутации категорически запрещены до завершения сверки.

## 7. Запрет скрытого исправления (No Silent Remediation)

Настоящий контракт явным образом устраняет исторические классы сбоев управления:
1. **Продолжение работы при несовпадении предусловий**: если состояние среды отличается от ожидаемого, операция обязана аварийно остановиться, а не пытаться продолжать выполнение.
2. **Маскировка повторного push**: представление выполнения команды, завершившейся сообщением «Everything up-to-date», как штатного первого проталкивания коммита недопустимо.
3. **Противоречие между README и первичными логами**: формирование сводок, противоречащих реальным машинным логам команд, запрещено.

Любое непредвиденное состояние требует остановки и предоставления объективных фактов Аудитору. Расширение области действия операции без нового манифеста запрещено.

## 8. Структурированное исполнение команд (Structured Command Execution)

> [!NOTE]
> Реализация механизма структурированного исполнения запланирована в рамках:
> **TO BE IMPLEMENTED IN DEC-003 PHASE 2**.

Целевой раннер управления исполнением обязан запускать команды не через непрозрачные строки шелла, а в виде строго структурированных процессов со следующими полями:
* `sequence: u64` — порядковый номер команды;
* `executable: String` — имя исполняемого файла (например, `git`, `gh`);
* `arguments: Vec<String>` — точный массив аргументов (например, `["status", "--short", "--untracked-files=all"]`);
* `cwd: PathBuf` — рабочий каталог;
* `mutating: bool` — флаг потенциальной мутации;
* `start_time_utc: DateTime` — время старта;
* `end_time_utc: DateTime` — время завершения;
* `exit_code: i32` — целочисленный код возврата операционной системы;
* `stdout_path: PathBuf` — путь к сохраненному сырому потоку вывода;
* `stderr_path: PathBuf` — путь к сохраненному сырому потоку ошибок.

## 9. Нативный захват процессов (Native Process Capture)

Для исключения неоднозначностей обработки вывода (например, специфичных для PowerShell ошибок обертки `NativeCommandError` при выводе нативных утилит в поток `stderr`):
* Раннер управления **ДОЛЖЕН (SHOULD)** использовать нативное системное API процессов (`System.Diagnostics.Process` в .NET / `std::process::Command` в Rust) с параметрами:
  * `UseShellExecute = false`;
  * `RedirectStandardOutput = true`;
  * `RedirectStandardError = true`.
* Потоки `stdout` и `stderr` **ОБЯЗАНЫ захватываться раздельно**.
* Код завершения процесса **ОБЯЗАН считываться непосредственно из дескриптора процесса**.

## 10. Пакет доказательств V1 (Evidence Bundle V1)

> [!NOTE]
> Переход на канонический формат Evidence Bundle v1:
> **REQUIRED AFTER DEC-003 PHASE 2 TOOLING IS ACCEPTED**.
> До этого момента используется legacy-формат bootstrap ZIP.

Канонический файл `artifact.zip` содержит строгую структуру:
```text
artifact.zip
├── manifest.json        # Неизменяемый манифест операции
├── summary.json         # Машиночитаемая выжимка результатов
├── commands.jsonl       # Построчный лог всех выполненных команд
├── checksums.sha256     # Контрольные суммы файлов архива кроме самого себя
├── evidence/            # Первичные потоки stdout/stderr каждой команды
│   ├── 001-git-fetch.stdout
│   ├── 001-git-fetch.stderr
│   └── ...
└── patches/             # Полные git diff / патчи изменений
    └── changes.patch
```

### Правила контрольных сумм `checksums.sha256` (Checksum Semantics):
* Файл `checksums.sha256` **ОБЯЗАН (MUST)** содержать записи SHA-256 для каждого обычного файла с содержимым внутри Evidence Bundle v1, **за исключением (`except` / `EXCEPT`) самого файла `checksums.sha256`**.
* Пути должны быть детерминированными и относительными к корню архива в каноническом формате:
  `<64 lowercase hex>  <relative/path>`
* Итоговый хэш SHA-256 самого ZIP-архива вычисляется отдельно строго **ПОСЛЕ** финализации архива и репортируется внешне как `ARTIFACT_SHA256`. Включение хэша ZIP внутрь самого архива запрещено.

### Правило разрешения конфликтов резюме (`summary.json` Conflict Rule):
* Файл `summary.json` формируется механически и носит исключительно вспомогательный характер.
* Если `summary.json` противоречит:
  * `manifest.json`;
  * `commands.jsonl`;
  * сырым потокам вывода `stdout` / `stderr`;
  * объектным свидетельствам Git;
  пакет доказательств признается **НЕСООТВЕТСТВУЮЩИМ ТРЕБОВАНИЯМ (NONCOMPLIANT)** и **КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН (MUST NOT)** приниматься как подтверждение успешного исполнения.

## 11. Контроль целостности артефактов (Artifact Integrity)

* При генерации артефакта раннер рассчитывает криптографический хэш SHA-256 сформированного ZIP-архива.
* Финальный машинный ответ Исполнителя обязан содержать:
  ```text
  RESULT: <COMPLETED | ALREADY_SATISFIED | STOPPED>
  OPERATION_ID: <operation_id>
  ARTIFACT: <absolute_path_to_artifact.zip>
  ARTIFACT_SHA256: <64_hex_sha256>
  STOP.
  ```
* Аудитор верифицирует соответствие хэша полученного архива заявленному значению `ARTIFACT_SHA256`.

## 12. Обработка пустого вывода (Empty Output)

* Пустой файл `stdout` признается валидным свидетельством только при наличии соответствующей записи в `commands.jsonl` с кодом возврата `exit_code: 0` и метками времени.
* Замена сырого пустого вывода произвольными текстовыми комментариями (например, `# clean working tree`) внутри канонического пакета `Evidence Bundle V1` **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНА**.

## 13. Изоляция временных файлов (Temporary Files)

* Все манифесты, промежуточные скрипты, временные тела PR и генерируемые архивы свидетельств **ДОЛЖНЫ размещаться в `%TEMP%`**.
* Временные файлы **КАТЕГОРИЧЕСКИ НЕ ДОЛЖНЫ (MUST NOT)** загрязнять рабочую копию репозитория (`working tree`).

## 14. Общие запрещенные действия по умолчанию (Global Forbidden Defaults)

Если иное прямо не предписано авторизованным манифестом операции, Исполнителю **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО (SHALL NOT)** выполнять:
* `git reset --hard` и `git clean -fd`;
* принудительную отправку (`git push --force`, force-push);
* удаление локальных или удаленных веток;
* переписывание истории (amend, rebase);
* произвольное расширение области редактируемых файлов.

## 15. Требование независимого аудита (Auditor Requirement)

Завершение выполнения скрипта Исполнителем **НЕ РАВНОЗНАЧНО** принятию работы. Архитектор / Аудитор независимо проверяет ссылки GitHub, состояние PR, коммиты и отчеты CI до авторизации следующего этапа.
