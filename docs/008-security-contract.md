# Контракт безопасности (Security Contract)

Документ определяет модель угроз, границы доверия, политики изоляции привилегий и правила защиты компонентов системы.

## 1. Модель угроз и границы ответственности (Threat Model & Scope)

### 1.1. Классификация субъектов
* **Ребенок (Child)**: Обладает учетной записью **Стандартного пользователя Windows (Standard User)**. Является потенциальным нарушителем, стремящимся обойти временные ограничения, продлить доступ в сеть или предотвратить выключение компьютера.
* **Родитель (Parent)**: Обладает учетной записью **Администратора Windows (Administrator)**. Является доверенным локальным и удаленным оператором системы.

### 1.2. Границы защищенности (Security Boundaries)
1. **Защита от стандартного пользователя (In Scope)**:
   * Стандартный пользователь НЕ ДОЛЖЕН (SHALL NOT) иметь возможности:
     * завершить, приостановить или модифицировать процесс службы `service`;
     * изменить, удалить или подменить конфигурационные файлы, базы данных состояния или бинарные файлы службы;
     * перехватить или модифицировать правила сетевой фильтрации `InternetGate`;
     * обойти блокировку интернета путем закрытия или принудительного завершения трей-приложения (`tray`);
     * выполнить привилегированные IPC-команды без знания родительского PIN-кода;
     * подобрать PIN-код путем неограниченного локального перебора (brute-force).
2. **Абсолютная защита от локального администратора (Out of Scope)**:
   * Защита от пользователя с полными правами локального администратора Windows (включая права `NT AUTHORITY\SYSTEM` или работу с загрузочных носителей) явно **НАХОДИТСЯ ВНЕ РАМОК СИСТЕМЫ**. Локальный администратор имеет техническую возможность удалить любую службу Windows или модифицировать реестр.

## 2. Изоляция компонентов и недоверенный статус трея

1. **Автономность службы при отсутствии сессии**:
   * Служба `service` сохраняет полную авторитетность и непрерывность принудительного исполнения даже при отсутствии интерактивной пользовательской сессии (на экране блокировки Logon/Lock Screen, при выходе пользователя из системы или до первого входа).
2. **Устойчивость к завершению `tray`**:
   * Процесс `tray` выполняется с минимальными правами стандартного пользователя.
   * Принудительное завершение (kill) процесса `tray` через Диспетчер задач, командную строку или аварийный сбой НЕ ОКАЗЫВАЕТ никакого влияния на:
     * отсчет и сохранение активных таймеров;
     * срабатывание блокировки интернета в заданный дедлайн;
     * срабатывание процедуры выключения компьютера;
     * прием команд и отправку уведомлений через Telegram.

## 3. Защита межпроцессного взаимодействия (IPC Security)

1. **Списки контроля доступа (ACLs / Security Descriptors)**:
   * Именованный канал (Named Pipe) создается службой с дескриптором безопасности, разрешающим подключение только аутентифицированным локальным пользователям машины.
   * Удаленные сетевые подключения к каналу запрещены на уровне ядра Windows.
2. **Имперсонация и валидация токенов**:
   * Служба `service` при обработке IPC-подключений может определять SID вызывающего процесса через API имперсонации Windows, предотвращая подмену идентификатора пользователя со стороны `tray`.

## 4. Защита секретов и авторизационных данных

1. **Хранение PIN-кода**:
   * Локальный PIN-код родителя хранится исключительно в виде криптографического хэша с солью (Argon2id) в защищенной системной директории службы (доступной только для `SYSTEM` и `Administrators`).
   * PIN-код никогда не передается в `tray` и не сохраняется в открытом виде.
2. **Защита токена Telegram**:
   * Токен Telegram Bot API хранится в зашифрованном виде (с использованием Windows DPAPI для системной учетной записи службы) или в конфигурационном файле, защищенном системным ACL.
