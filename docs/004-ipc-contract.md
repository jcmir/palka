# Контракт межпроцессного взаимодействия (IPC Contract)

Документ определяет спецификацию протокола взаимодействия между привилегированной службой `service` и непривилегированным приложением в трее `tray`. Все типы данных соответствуют [Доменному контракту](file:///c:/PALKA/docs/002-domain-contract.md).

## 1. Архитектура и границы доверия IPC

1. **Транспорт (Transport)**:
   * Локальные именованные каналы Windows (Windows Named Pipes) с детерминированным путем в пространстве ядра (например, `\\.\pipe\palka_ipc_v1`).
   * Канал ДОЛЖЕН (SHALL) быть сконфигурирован со строгими дескрипторами безопасности (Security Descriptor / ACL), разрешающими чтение и запись локальным интерактивным пользователям, но запрещающими доступ по сети (Network Access Denied).

2. **Модель доверия (Trust Model)**:
   * Клиент `tray` рассматривается службой как **недоверенный (Untrusted)**.
   * `service` никогда не доверяет утверждениям клиента о правах или аутентичности без криптографической/авторизационной проверки.
   * Все параметры команд подвергаются строгой валидации на стороне `service`.

## 2. Разделение команд по требованиям к авторизации

Все IPC-запросы делятся на две строгие категории:

### 2.1. Не требующие авторизации (Unprivileged / No PIN required)
Доступны любому запущенному экземпляру `tray` в пользовательской сессии:
* `QueryStatus` — запрос текущего состояния системы (`InternetState`, `ShutdownState`, активные таймеры, `ServiceHealth`).
* `SendChildMessage { text }` — отправка текстового сообщения от ребенка родителям в Telegram.
* `SubscribeEvents` — подписка на входящий поток событий (`WarningEvent`, новые сообщения от родителей, смена статуса).

### 2.2. Защищенные PIN-кодом (PIN Protected / Privileged)
Требуют передачи криптографически стойкого токена авторизованной сессии или валидного PIN-кода родителя в теле команды:
* `ScheduleInternetBlock { duration_minutes }` (при вызове из локального трея);
* `ImmediateInternetBlock`;
* `CancelInternetBlockTimer`;
* `RestoreInternet` (снятие блокировки интернета);
* `ScheduleShutdown { duration_minutes }`;
* `CancelShutdownTimer`.

## 3. Протокол проверки PIN-кода (Authoritative PIN Protocol)

1. **Авторитетная валидация**:
   * Валидация введенного PIN-кода производится исключительно в `service`.
   * Хэш PIN-кода (с использованием стойкой функции хэширования паролей, например Argon2id) хранится в защищенном хранилище службы и недоступен процессу `tray`.
2. **Анти-брутфорс и блокировки (Rate Limiting & Lockout)**:
   * `service` ведет авторитарный счетчик неудачных попыток ввода PIN.
   * После 3 (трех) подряд неверных попыток служба ДОЛЖНА (SHALL) активировать временную блокировку проверки PIN (экспоненциальная задержка: 30 секунд, 1 минута, 5 минут).
   * Информация о блокировке возвращается в `PinAuthenticationResult { success: false, lock_timeout_seconds: Some(...) }`.
3. **Сессионный токен**:
   * При успешной валидации PIN служба может вернуть короткоживущий токен сессии администратора (TTL не более 5 минут), позволяющий выполнить административное действие без повторного ввода PIN.

## 4. Двусторонний чат и события (Chat & Event Streaming)

1. **Поток событий (Service -> Tray)**:
   * При подключении `tray` служба отправляет текущий полный снимок состояния (`StatusSnapshot`).
   * В процессе работы служба асинхронно пушит события `Event` (включая `WarningThresholdReached`, `ChatMessageReceived`, `InternetStateChanged`).
2. **Маршрутизация сообщений (Tray -> Service -> Telegram)**:
   * Сообщение ребенка проверяется на длину и допустимые символы.
   * `service` присваивает сообщению `MessageId`, сохраняет его в очередь и инициирует асинхронную отправку в Telegram.
   * Результат доставки или ошибки обновляет статус сообщения.
